\featuredapplication{ProcRosetta learns a shared behavior-aware representation for retrieving related event logs, process trees, and Petri nets across artifact types.}

\abstract{Process mining relies on event logs, process trees, and Petri nets, yet comparing behavior across these different representations remains difficult. We present \model, a behavior-supervised framework that maps all three artifact types into a shared representation space. Training on behavioral families teaches the model to bring related artifacts closer while preserving meaningful differences in ordering and concurrency. On a fixed 48-family evaluation subset, the learned space supports within-type and cross-artifact retrieval. \model also includes a grammar-constrained decoder that produces well-formed process trees convertible to Petri nets under the evaluated protocol. These structural guarantees do not ensure behavioral correctness: the generated process trees remain less faithful than models produced by specialized process discovery, and tests on two external event logs reveal a clear generalization gap. \model is therefore best viewed as a representation and retrieval framework that can also propose candidates for independent behavioral validation and analyst review. The results highlight the promise of behavior-aware retrieval across process mining artifacts while showing that reliable cross-artifact generation remains an open challenge. The code, data, and trained model are publicly available.}

\keyword{process mining; cross-artifact retrieval; representation learning; behavior supervision; event logs; process trees; Petri nets; grammar-constrained decoding}

\section{Introduction}\label{sec:introduction}

Process mining work rarely begins and ends with a single representation. Operational systems produce event logs, process discovery algorithms return process trees or Petri nets, and analysts maintain reference models, variants, and versions across repositories. These artifacts can describe closely related behavior while differing fundamentally in structure. A practical repository may therefore contain raw event logs, models discovered by different algorithms, curated reference Petri nets, and versions contributed by different departments or organizations. The resulting question is direct: given an event log or process model, can an analyst retrieve behaviorally related artifacts expressed in another representation?

Figure~\ref{fig:intuitive-example} illustrates the opportunity. The same small process can be observed as a finite event log, organized as a process tree, or represented explicitly as a marked Petri net. A common space can support three concrete uses: querying a model repository with an event log, reusing a related model across notations, and retrieving reference models before proposing and validating a candidate. These uses do not require the system to claim behavior-preserving translation. A finite event log contains only observed executions, different structures can generate the same visible traces, and even equal trace languages can conceal different concurrency or causal relations.

\input{figures/intuitive-example}

Existing process mining representation-learning methods predominantly encode one artifact type or optimize one downstream task. Process model similarity methods usually assume a common notation, whereas process discovery methods construct a model from an event log but do not learn a retrieval space spanning event logs and multiple model formalisms. What remains insufficiently studied is behavior-supervised alignment across heterogeneous process artifacts, particularly where syntactic and behavioral similarity diverge.

We introduce \model, which treats event logs, process trees, and marked Petri nets as three representations of process behavior. Modality-specific encoders map each input to a shared vector for comparison and retrieval. Training groups a process tree, alternative Petri net realizations, and several event log observations into behavior families. These families help the model ignore superficial differences while retaining important behavioral distinctions, including ordering and concurrency. A secondary grammar-constrained decoder proposes a process tree from any supported input.

The intended operating model is to \emph{retrieve, propose, and validate}. A query artifact retrieves related models or event logs, and the decoder may propose a process tree candidate. Behavioral and soundness checks, together with analyst review, determine whether the result is usable. \model addresses representation alignment, retrieval, and constrained candidate proposal. It is not a replacement for specialized process discovery or model validation methods. In particular, its decoder guarantees output well-formedness under the stated protocol, not behavioral equivalence to the source.

The evaluation separates two capabilities that are easy to conflate: learning a useful common representation and generating a behaviorally faithful process model. We test on families that are absent from training but are generated under the same synthetic design. Within this scope, the paper asks:

\begin{description}
\item[\RQone:] To what extent does behavior-supervised training produce representations that are invariant to artifact notation while remaining sensitive to relevant behavioral differences?
\item[\RQtwo:] How accurately can event logs, process trees, and Petri nets retrieve behaviorally related artifacts across modalities under the evaluated protocol, and how does the learned geometry compare with deterministic behavioral features?
\item[\RQthree:] To what extent does grammar-constrained decoding guarantee structurally admissible process trees, and how faithfully do the generated candidates preserve source behavior?
\end{description}

The paper makes five contributions. First, it formulates behavior-aware alignment and retrieval among event logs, process trees, and Petri nets as a cross-artifact process mining task. Second, it introduces behavior-family supervision in which relations are controlled by behavioral properties rather than surface pairing alone. Third, it proposes a multimodal architecture and relation-aware objective for within-modal and cross-modal retrieval. Fourth, it provides grammar-constrained candidate generation while separating syntactic validity and Petri net convertibility from measured behavioral fidelity. Fifth, it releases the generated benchmark, external event log stress tests, baselines, checkpoint records, and implementation needed to inspect both successful and unsuccessful behavior.

\section{Related Work}\label{sec:related}

\subsection{Process Model Similarity, Matching, and Repository Search}

Process model relations may be defined over labels, graph structure, executable traces, or behavioral ordering relations \cite{Dijkman2011}, \cite{Schoknecht2017SimilaritySurvey}, and \cite{Zampino2026BehavioralSimilarity}. Observed-behavior measures compare executions \cite{deMedeiros2008ObservedBehavior}, whereas behavioral profiles summarize ordering and exclusiveness between activities \cite{Weidlich2011BehavioralProfiles}. Workflow embeddings and Siamese graph networks support efficient similarity-based candidate retrieval within workflow-model collections \cite{Klein2019WorkflowEmbeddings,Hoffmann2020SiameseWorkflowRetrieval}. These approaches motivate repository search, but generally assume a common model representation. \model instead asks whether an event log, a process tree, or a marked Petri net can query a candidate collection expressed in another representation.

Conformance checking addresses a related but distinct question. Fitness measures whether a model can reproduce observed executions; precision measures whether it permits substantially more behavior than those observations support \cite{Adriansyah2013}. Directly-follows summaries are cheaper but omit longer-range dependencies and can conceal concurrency \cite{vanDerAalst2019DFG}. Retrieval can therefore identify candidates before conformance checking, but a high retrieval rank is not itself a certificate from conformance checking.

\subsection{Representation Learning for Event Logs and Process Models}

Trace encodings range from handcrafted features to sequence models \cite{Barbon2023}. Prior work learns representations at activity, trace, event log, or model level \cite{DeKoninck2018}, and graph-based embeddings represent Petri nets \cite{Colonna2024}. Representation learning is also used in predictive monitoring \cite{Berti2026ICFM}, where the goal is to predict properties of ongoing cases rather than align complete event logs with formal process models. In contrast, \model learns native encoders for finite event logs, hierarchical process trees, and marked Petri nets, with all three projected into one retrieval space.

\subsection{Automated and Neural Process Discovery}

Classical process discovery maps finite event logs to generalizing process models, with methods trading fitness, precision, simplicity, scalability, and representational bias \cite{Augusto2019DiscoveryBenchmark}. Inductive Miner recursively detects cuts and returns a sound block-structured model \cite{Leemans2013}; Split Miner targets accurate, simple BPMN models and may express non-block-structured dependencies \cite{Augusto2019SplitMiner}. Learned process discovery estimates process structure from examples, including with graph neural networks \cite{Sommers2023}. Natural-language-to-model generation and specialized language models provide further structured-generation settings \cite{Kourani2024LLMProcessModeling,Berti2025RLProcessModeling}.

Retrieval, process discovery, and candidate generation must be distinguished. Process discovery constructs a model from an event log; retrieval searches an existing collection of candidate models; candidate generation proposes a model that still requires validation. Only event log to process tree decoding overlaps directly with classical process discovery in this study, so Inductive Miner is a baseline for that decoding task, not for cross-artifact retrieval.

\subsection{Multimodal and Multi-View Representation Learning}

General multimodal-learning taxonomies cover representation, alignment, and translation across heterogeneous views \cite{Baltrusaitis2019Multimodal}. Paired observations can define a common space without identical encoders \cite{Radford2021}; supervised contrastive objectives allow several members of a semantic class to act as positives \cite{Khosla2020}; and regularization of variance and covariance discourages collapse \cite{Bardes2022}. Process artifacts are unusual views because they differ in observability, abstraction, and behavioral semantics. In process mining, ``multimodal'' can also mean augmenting event data with video, audio, sensors, text, or images \cite{Gavric2025MultimodalEvidence,Pasquadibisceglie2026MultimodalPPM}. We therefore use \emph{cross-artifact} for alignment among alternative process representations.

\subsection{Grammar-Constrained Structured Prediction}

Grammar-aware latent-variable models and grammar-constrained decoding restrict generation to syntactically admissible structures \cite{Kusner2017GrammarVAE,Geng2023}. Formal transformations provide stronger guarantees on narrower domains: conversion from a workflow Petri net to a process tree can return an equal-language process tree when its applicability conditions hold \cite{vanZelst2020NetToTree}. A valid process tree likewise has a standard Petri net interpretation \cite{vanDerAalst2016}. \model always attempts a process tree proposal, including where an exact projection may not exist, and therefore separates output admissibility from behavioral fidelity.

\subsection{Synthetic Process Generation and Benchmark Construction}

Synthetic families provide exact control over structural contrasts, repeated observations, and split membership. They also create a generator-specific notion of generalization. Abstraction-based process discovery and event-structure approaches illustrate other semantic bridges between event logs and models \cite{vanDerAalst2018Abstractions,Dumas2015EventStructures}, while partial-order process mining shows why total-order traces alone can hide concurrency \cite{Leemans2023PartialOrderSurvey}. The present benchmark records visible-language and partial-order relations separately, but it does not provide a behavioral-equivalence oracle for arbitrary external artifacts.

\section{Problem Definition}\label{sec:setting}

\subsection{Heterogeneous Process Artifacts}

Event logs, process trees, and Petri nets are \emph{heterogeneous process artifacts}: they can refer to the same process behavior, but they do not contain the same kind or amount of information. An event log records executions that happened to be observed. A process tree and a Petri net are executable models that describe behavior that may occur, including paths that are absent from a particular log. Moreover, process trees organize behavior hierarchically, whereas Petri nets encode state and routing in a graph. The difference is therefore not merely one of file format or serialization; it concerns \emph{observability}, \emph{structure}, and \emph{behavioral semantics}.

Let $\mathcal{A}$ be a finite activity alphabet and $\tauact$ an invisible activity. A trace $\sigma\in\mathcal{A}^{*}$ is one finite sequence of visible activities, and an event log $L$ is a finite multiset of such traces. The word ``multiset'' is important: if ten cases follow $\langle a,b\rangle$ and one follows $\langle a,c\rangle$, the log retains those empirical frequencies. However, the absence of $\langle a,c\rangle$ from a smaller sample does not prove that the underlying process forbids it. An event log is thus a \emph{finite observation}, not a complete behavioral specification.

A process tree $T$ is generated by
\begin{equation}
T ::= a \mid \tauact \mid \mathsf{SEQ}_{k}(T_1,\ldots,T_k)
 \mid \mathsf{XOR}_{k}(T_1,\ldots,T_k)
 \mid \mathsf{AND}_{k}(T_1,\ldots,T_k)
 \mid \mathsf{LOOP}(T_1,T_2),
\label{eq:grammar}
\end{equation}
where $a\in\mathcal{A}$ and $k\geq2$. The operator $\mathsf{SEQ}$ executes its children in order, $\mathsf{XOR}$ selects one child, and $\mathsf{AND}$ permits concurrent execution of its children. In $\mathsf{LOOP}(T_1,T_2)$, the body $T_1$ executes at least once and the redo branch $T_2$ determines how another iteration is entered. This grammar gives a compact, \emph{block-structured specification}, but it cannot express every valid Petri net topology.

A labeled Petri net is a tuple $N=(P,U,F,\ell,m_0,m_f)$ with places $P$, transitions $U$, flow relation $F$, labels $\ell:U\rightarrow\mathcal{A}\cup\{\tauact\}$, and initial and final markings $m_0,m_f$. Tokens in the marking determine which transitions are enabled, so a Petri net represents choices, synchronization, and concurrency through its execution state. Transitions labeled $\tauact$ can change that state without adding a visible activity to a trace. A Petri net is consequently a \emph{state-based process model}, rather than a hierarchical expression or a sample of executions.

These differences make literal matching unsuitable. Two models can have different nodes and routing structures yet permit the same visible executions; conversely, the same finite log can be compatible with several models that differ on unobserved behavior or concurrency. The relevant correspondence is therefore a \emph{declared behavioral relation}, not equality of syntax, identifiers, or observed frequencies.

Consider a process that first registers a request and then either accepts or rejects it. One process tree representation is
\begin{equation}
T=\mathsf{XOR}\bigl(
  \mathsf{SEQ}(\textsf{register},\textsf{accept}),
  \mathsf{SEQ}(\textsf{register},\textsf{reject})
\bigr).
\label{eq:worked-family}
\end{equation}
The tree contains two distinct leaves with the visible label \textsf{register}, one in each exclusive-choice branch. A corresponding Petri net realization, $N^{(1)}$, likewise has a separate \textsf{register} transition on each branch. Another realization, $N^{(2)}$, factors out the repeated prefix: it uses one shared \textsf{register} transition and then two silent routing transitions that select \textsf{accept} or \textsf{reject}. Thus $N^{(1)}$ and $N^{(2)}$ differ in their numbers of visible transitions and in their routing graphs, but both allow exactly
\[
\langle\textsf{register},\textsf{accept}\rangle
\quad\text{and}\quad
\langle\textsf{register},\textsf{reject}\rangle.
\]
This is a concrete example of \emph{structural non-uniqueness}: different internal models describe the same visible trace set. A \emph{trace variant} is one distinct sequence of visible activities; repeated occurrences of that sequence belong to the same variant.

To complete the example, consider how the same behavior appears in an event log. Every completed case records one of the two traces above. However, an event log contains only a finite number of cases, so two logs observed from the same process need not contain the two variants in the same proportions. One log may contain the accept and reject variants about equally often, while another may contain mostly accept cases and only a few reject cases. This difference reflects \emph{observational variation}: the cases happened to be sampled with different frequencies, but the set of behavior permitted by the process has not changed.

The dataset uses two complementary observations to make the distinction between process behavior and finite sampling visible during learning. The \emph{coverage-oriented observation}, denoted $L^{(u)}$, cycles through the available trace variants before repeating them. It therefore presents the model with broad coverage of the known trace pool. The \emph{independently sampled observation}, denoted $L^{(r)}$, draws traces with replacement and can therefore contain an uneven empirical distribution. The first observation reduces accidental omissions; the second exposes the model to the frequency variation that naturally arises in finite samples. Neither observation is treated as a complete description of the process.

We can now explain why the training data are organized into \emph{behavior families}. For the worked example, the family contains one process tree target $T$, two structurally different Petri net realizations $N^{(1)}$ and $N^{(2)}$, and two finite event log observations $L^{(u)}$ and $L^{(r)}$. Pairing each Petri net with each event log produces the four aligned rows in Table~\ref{tab:worked-family}. The process tree appears in every row because it is the common decoding target, not because four different process trees were created.

The four rows represent one related group, not four independent processes. Within the group, changing $N^{(1)}$ to $N^{(2)}$ isolates \emph{structural variation}: the routing graph changes while the visible trace set remains the same. Changing $L^{(u)}$ to $L^{(r)}$ isolates \emph{observational variation}: the sampled cases and their frequencies change while their source behavior remains the same. Presenting both forms of variation helps the representation learn that node identities, routing layout, case order, and empirical trace frequency are not by themselves reliable indicators of behavioral difference.

Keeping the complete family in one training, validation, or test split is equally important. If related rows were divided across splits, the system could be evaluated on another view of a process it had already seen during training. Family-level splitting prevents this direct leakage. Within a split, family membership identifies which artifacts belong to the same comparison group. It does not, by itself, claim that every pair is equivalent under every behavioral semantics; the relation record introduced in the next subsection specifies the exact relation used for supervision.

Finally, the family uses one \emph{designated process tree target} because supervised decoding requires a single reference output. This is a dataset convention, not a uniqueness claim. Several process trees may be compatible with the same finite event log, especially when the log omits possible behavior. The designated target provides a consistent training signal, while the grammar restricts generated outputs to well-formed, block-structured process trees that can be converted into Petri nets.

\subsection{Behavioral Relations and Equivalence Levels}

The previous subsection grouped several artifacts around one process tree. This raises a central question: \emph{what does it mean for two process artifacts to describe the same behavior?} Structural equality is too strict because the duplicate-prefix nets $N^{(1)}$ and $N^{(2)}$ have different routing graphs but allow the same visible executions. At the same time, equality of visible traces can be too weak because it does not always preserve information about causality or concurrency. Finally, agreement with a finite event log says only that a model can explain the observed cases; it does not establish agreement on behavior that the log never recorded.

The paper therefore records behavioral agreement along two separate semantic dimensions. \emph{Visible-language agreement} means that two process models permit the same complete set of visible activity sequences. \emph{Partial-order agreement} means that they also agree on the recorded ordering and concurrency relations between activities. When analysis observes matching behavior only within a search limit, the result is retained as \emph{bounded evidence}; it is not promoted to a claim of complete-language equivalence.

For example, one model may allow \textsf{check credit} and \textsf{prepare invoice} to run in parallel, while another explicitly allows either sequential order. Both models permit the visible traces $\langle\textsf{check credit},\textsf{prepare invoice}\rangle$ and $\langle\textsf{prepare invoice},\textsf{check credit}\rangle$, so they have visible-language agreement. Only the first model represents the activities as concurrent, so they do not have partial-order agreement.

Keeping these dimensions separate makes the supervision explicit. A pair that agrees under both recorded semantics can be used as a strong positive example. A pair with the same visible language but a different partial-order relation is still behaviorally related, but it receives weaker supervision so that the model is not taught to erase the concurrency difference. Bounded evidence never creates an exact positive. The later methods section describes how these relations are established and checked.

This distinction also explains the role of a \emph{behavior family}. A family is a data-generation and split unit that collects artifacts which should be compared with one another. It is deliberately broader than an equivalence class. Family membership places artifacts in the same controlled comparison; it does not declare them identical under every semantics. The family's relation record states the more precise relationship and determines how each comparison is used during training.

To describe the contents of a family clearly, we use three terms for three different roles:
\begin{itemize}
\item The \emph{underlying specification} is the original process tree on which the family is based. In the request example, it is the tree in Eq.~\eqref{eq:worked-family}. It provides the common reference for the family.
\item An \emph{artifact realization} is a concrete process model representing that specification. In the request example, the duplicated-prefix Petri net and the shared-prefix Petri net are two realizations. They use different structures to represent the same visible traces.
\item A \emph{finite observation} is an event log containing cases sampled from the process. The coverage-oriented and independently sampled logs are two observations. They can contain different trace frequencies because neither log records every possible execution of the process.
\end{itemize}
These terms describe different roles, not different degrees of correctness. The specification anchors the family, a realization models its behavior, and an observation records a finite sample of that behavior.

For a family identified by $f$, we write $T_f$ for the underlying process tree, $N_f^{(1)}$ and $N_f^{(2)}$ for the two Petri net realizations, and $L_f^{(u)}$ and $L_f^{(r)}$ for the two event log observations. Here, $u$ denotes the coverage-oriented observation and $r$ the independently sampled observation. A stored row combines $T_f$, one of the two Petri nets, and one of the two event logs. Using every such combination produces the four rows shown in Table~\ref{tab:worked-family}. Keeping $T_f$ fixed while changing the Petri net isolates structural variation; keeping the Petri net fixed while changing the event log isolates observational variation.

For readability, this notation shows the activities using their original names. The stored data use consistent neutral activity names within each row, as explained in Section~\ref{sec:relations}. This renaming can make two artifacts from the same family look different at the label level without changing their recorded relationship. The relation record, rather than surface labels, therefore determines how the artifacts are compared.

\subsection{Cross-Artifact Retrieval Task}

Process repositories often contain different representations of related behavior. An analyst may have an event log from a running system but need to find an existing Petri net for comparison. Conversely, an analyst may have a process tree and want to find event logs that exhibit similar behavior. Ordinary lookup is insufficient in these cases: an event log has neither the nodes of a process tree nor the places and transitions of a Petri net. The artifacts must be compared through their behavior rather than through a common file structure.

The goal of \emph{cross-artifact retrieval} is to rank existing artifacts of one type using a query of another type. For example, the request event log introduced earlier can be used to search a collection of Petri nets. The duplicated-prefix net and the shared-prefix net should both rank highly because they represent the relevant request behavior, even though neither is structurally identical to the log or to the other net. The same task can be reversed: a Petri net can query a collection of event logs, or a process tree can query a collection of Petri nets.

Retrieval searches among artifacts that already exist. It does not translate the query, construct a new process model, or select a final model for the analyst. Its output is simply an ordered list in which candidates judged more behaviorally related to the query appear earlier. This makes retrieval useful as a first step for finding precedents, related variants, or models that can subsequently be examined through conformance checking and analyst review.

To compare the three artifact types, \model maps each of them into the same vector space. We use $m\in\{T,L,N\}$ to denote the artifact type: $T$ for process trees, $L$ for event logs, and $N$ for Petri nets. Each type has its own encoder because its native structure is different. Nevertheless, all three encoders produce vectors with the same dimension, so a vector obtained from an event log can be compared directly with one obtained from a process tree or Petri net.

Each encoder produces two outputs with different purposes. The \emph{contextual memory} $H_m$ retains several local representations, such as information about individual activities or graph nodes. It is used later by the decoder when detailed structure is needed for candidate generation. The \emph{retrieval vector} $\vect z_m$ compresses the complete artifact into one fixed-size summary and is normalized to unit length. Only this compact vector is needed to rank retrieval candidates.

Let $q$ be a query artifact and $c$ one candidate from the collection being searched. Their retrieval score is the cosine similarity between their normalized vectors:
\begin{equation}
\operatorname{score}(q,c)
=\cos(\vect z_q,\vect z_c)
=\vect z_q^{\mathsf T}\vect z_c.
\label{eq:retrieval-score}
\end{equation}
A larger score places the candidate earlier in the ranked list. Because the vectors share one space, the same rule applies to every direction, including event log to Petri net, Petri net to process tree, and process tree to event log retrieval.

The meaning of a \emph{relevant candidate} follows the behavioral relations defined above. It is not determined by identical labels, matching serializations, or membership in the same family alone. The evaluation uses the relation appropriate to the experiment to decide which candidates count as relevant. A high retrieval score therefore means that the learned representation predicts a behavioral relationship; it is not a proof of equivalence, soundness, or conformance. Any retrieved model intended for reuse must still be validated independently.

\subsection{Constrained Candidate-Generation Task}

Retrieval is useful when the repository already contains an appropriate artifact. In some situations, however, no existing candidate adequately represents the behavior of interest. An analyst may then want the system to propose a new process model from an event log, a Petri net, a process tree, or a combination of available artifacts. This motivates a second task: \emph{candidate generation}.

The task produces a process tree in the grammar of Eq.~\eqref{eq:grammar}. Using one output type gives all supported inputs a common destination. Process trees are suitable for this role because their hierarchical grammar is compact, can be checked while it is generated, and has a standard conversion to a Petri net. The choice also imposes an important limitation: the decoder can propose only block-structured behavior, even when the source Petri net has a more general topology.

For example, consider the event log in the earlier request example. Each case first records \textsf{register} and then records either \textsf{accept} or \textsf{reject}. From this log, the decoder may propose a tree that performs \textsf{register} before choosing between the two outcomes. Given either Petri net from the same example, it should aim for a process tree that captures the same visible behavior. The output does not need to reproduce the source's internal graph because a process tree and a Petri net organize behavior differently.

When generation uses one source artifact, the decoder reads its \emph{contextual memory} $H_m$. This memory retains local information that the single retrieval vector cannot preserve, such as activity order in a trace, relations between parents and children in a process tree, or neighboring nodes in a Petri net. The decoder attends to these details while choosing the operators, activities, and structure of the output tree. We call this the \emph{direct-generation} setting.

Generation can also use more than one artifact. For example, an event log may provide evidence about executions while a related Petri net provides explicit routing information. To offer a simple common interface for such inputs, \model averages their normalized retrieval vectors. For a set $S$ of available artifact types, the fused representation is
\begin{equation}
\vect z_{\mathrm{fuse}}=\frac{1}{|S|}\sum_{m\in S}\vect z_m,
\qquad S\subseteq\{T,L,N\},
\label{eq:fusion}
\end{equation}
The mean is projected into a memory that the same process tree decoder can read. This \emph{fusion} mechanism treats all available inputs equally. It does not learn that one source may be more reliable than another, and it does not explicitly resolve disagreements between them. It is therefore a baseline for testing whether the shared representation contains enough compatible information to support generation from multiple artifact types.

The word \emph{constrained} refers to how the output is formed. At each decoding step, the process tree grammar masks choices that would make the expression invalid. The decoder must fill every required child position, may emit only permitted token types and activity labels, and may finish only after the tree is complete. Under the evaluated protocol, these constraints ensure that the output can be parsed as a process tree and converted into a Petri net. They prevent malformed structures; they do not determine which valid structure best represents the source.

For this reason, every output is called a \emph{candidate}. A syntactically valid tree can still omit an activity, introduce an incorrect choice, serialize behavior that should be concurrent, or permit traces unsupported by the source. Candidate generation therefore does not provide a behavior-preserving translation guarantee and does not replace process discovery or conformance checking. Its role is to propose a structurally admissible model that can then be evaluated behaviorally and reviewed by an analyst. One evaluation method used later is \emph{behavioral simulation}: the candidate is executed repeatedly to obtain traces, and summaries of those traces are compared with summaries of the reference behavior.

Together, behavior-aware representation learning, cross-artifact retrieval, and constrained candidate generation define the three tasks examined by \RQone, \RQtwo, and \RQthree{} in the Introduction.

\section{Materials and Methods}\label{sec:model}

\subsection{Behavior families as the supervision unit}\label{sec:corpus}

Learning a common representation requires examples that show both \emph{which differences should be ignored} and \emph{which differences should be preserved}. A single aligned triple containing one process tree, one event log, and one Petri net provides too little information. Because the three artifacts always occur together, the model could associate them through accidental details rather than through behavior. It might rely on a particular transition identifier, the order in which a Petri net was serialized, or the trace frequencies in one finite log. Such shortcuts can fit the training rows without producing a representation that generalizes to another realization or observation of the same process.

Behavior families are designed to expose these shortcuts. As introduced in Section~\ref{sec:setting}, each family contains one designated process tree, two Petri net realizations, and two event log observations. The Petri nets provide alternative model structures, while the event logs provide alternative finite samples. Because these artifacts are varied within the same family, the training objective can compare them while holding their known behavioral relationship fixed.

The two Petri net realizations teach the model not to depend on one internal encoding. For example, two equivalent nets may use different place names, transition identifiers, or serialization orders. They may also express routing differently, as in the duplicate-prefix example, where one net duplicates a visible transition and the other shares it through silent routing. When the recorded relation certifies agreement, these differences should not move the artifacts far apart in the shared representation.

The two event log observations address a different source of variation. Logs sampled from the same trace pool can present traces in a different order and with different empirical frequencies. One observation may contain two variants in similar proportions, whereas the other may be dominated by one variant. Showing both observations teaches the system that these sampling effects do not necessarily indicate a different underlying process.

The designated process tree serves another purpose. The decoder needs one reference output when it learns to generate a process tree from an event log, a Petri net, or a fused input. Several process trees may be compatible with the same finite evidence, but assigning one target within each family provides a consistent supervised output. This choice is a dataset convention and does not claim that the designated tree is the only behaviorally acceptable model.

Calling the family the \emph{supervision unit} means that training comparisons and split decisions are defined at the family level, even though the artifacts are stored in four separate rows. Members of a family supply positive or weaker relational examples for the representation losses, and their common process tree supplies the target for generation. The family structure therefore provides more information than any row considered in isolation.

Family membership alone does not determine that every pair should be treated as fully equivalent. The accompanying relation metadata specifies the appropriate learning signal. When two realizations agree in both complete visible language and the recorded partial-order semantics, they can be used as a \emph{strong positive}: the model is encouraged to place them close together. Ordinary families, duplicate-prefix families, and accepted M-pattern families can provide such pairs when their recorded identifiers agree.

The concurrency/interleaving families illustrate why relation metadata is necessary. Their two realizations allow the same visible traces, but one represents true concurrency and the other represents an explicit choice between sequential orders. Treating them as an unconditional positive would teach the model to erase this distinction. The distinction is enforced during training, after the artifacts in a batch have been mapped to normalized vectors in the shared space. Their metadata marks them as having the same exact trace-language identifier but different partial-order identifiers. The hierarchical loss $\mathcal{L}_{\mathrm{hier}}$, defined in Section~\ref{sec:training}, then encourages the following distance order: pairs agreeing under both semantics are closest; pairs agreeing only in visible language come next; pairs that merely belong to the same family are farther apart; and unrelated pairs are farthest apart. Thus the signal is weaker because it places the pair in the same broad behavioral neighborhood without aligning it as tightly as a strong positive pair.

After these design choices, constructing a family follows six steps:
\begin{enumerate}
\item choose either an ordinary random structure or a controlled behavioral motif;
\item construct the designated process tree;
\item construct two related Petri net realizations;
\item establish and record their visible-language and partial-order relations;
\item construct a trace pool and derive two finite event log observations; and
\item apply consistent activity names within each observation and store the four combinations of Petri net realization and event log observation.
\end{enumerate}
Figure~\ref{fig:corpus} summarizes the procedure. The first stage defines the underlying process tree or controlled motif. The second creates the alternative Petri net structures and records how their behavior is related. The third derives two finite observations from the common trace pool. The final stage applies observation-specific activity mappings and stores every pairing of a Petri net with an event log. Importantly, the behavioral relations and family identity are established before this row expansion.

\input{figures/corpus}

All four rows from a family are assigned to the same training, validation, or test split. This prevents direct leakage. Without family-level splitting, the model could train on one Petri net or event log from a family and then be tested on a closely related realization or observation from that same family. Keeping the family intact ensures that evaluation uses families not encountered during training.

This split rule has a precise limitation. Families are kept intact, but independently generated families are not globally deduplicated by their normalized process trees or complete visible languages. Two different families can therefore happen to describe the same behavior. The reported experiments measure generalization to \emph{unseen generated families}; they do not establish strict behavior-disjoint generalization or robustness to a different data generator.

\subsection{Ordinary random families and controlled anchor families}\label{sec:anchor-families}

The training corpus must satisfy two different needs. First, it needs enough structural variety to expose the model to many process shapes, sizes, and activity arrangements. Second, it needs carefully chosen examples in which one behavioral distinction changes while the surrounding context remains stable. Random examples are useful for \emph{breadth}, but they do not guarantee that rare or subtle contrasts will occur. Hand-designed examples provide \emph{controlled diagnosis}, but they cover only a narrow part of the process space. The corpus therefore combines \emph{ordinary random families} with \emph{controlled anchor families}.

\emph{Ordinary random families} provide broad structural coverage. Their process trees are generated \emph{topology first}: the generator chooses the control-flow operators and recursively builds an unlabeled tree before assigning any activity names. This order separates the process structure from the labels placed on its leaves. A sampled topology is rejected if it does not contain enough leaf positions for the required minimum number of distinct activities.

Activity assignment begins only after the topology has been accepted. The generator first gives different labels to enough leaves to reach the required activity count. It may reuse labels on the remaining leaves. As a result, repeated activities can occur naturally, but label reuse cannot prevent the family from meeting its minimum activity requirement. More importantly, the activity requirement does not alter the already sampled control-flow structure.

Random generation can produce several syntactic forms for essentially the same process tree. The generator therefore normalizes every target before measuring or storing it. It first places the children of XOR and parallel operators in a canonical order and then applies the folding procedure used throughout the study. Folding removes redundant silent leaves, merges nested operators of the same type, and simplifies empty or single-child constructs. The result is called the \emph{folded process tree}. All reported tree sizes, depths, exact matches, and edit distances use this normalized form so that redundant syntax does not determine the measured complexity.

Each ordinary family belongs to a profile that specifies allowed ranges for folded size, depth, and number of visible activities. A sampled tree is retained only if it satisfies the complete profile. If it does not, the generator starts again instead of adding artificial sequential branches to make the tree large enough. If repeated attempts remain unsuccessful, construction fails explicitly rather than silently weakening the profile. This policy keeps the meaning of each complexity profile fixed.

The complexity profiles also support \emph{curriculum learning}. Training the encoders and process tree decoder immediately on the largest structures would require them to learn activity correspondence, cross-artifact alignment, and long structured outputs at the same time. The curriculum begins with shorter and shallower families, then introduces larger and deeper families as training progresses. This lets the model establish basic alignment and grammar handling before facing the full structural range. The three complexity corpora are named \texttt{simple}, \texttt{medium}, and \texttt{complex}; the corresponding curriculum stages use the same names and retain examples from earlier corpora for rehearsal. Section~\ref{sec:curriculum} specifies the transition criteria and mixtures.

\emph{Controlled anchor families} serve a different purpose. Each anchor places one small, known representation contrast inside a randomized surrounding context. The same context is used for both realizations, so the intended contrast is not mixed with unrelated structural changes. This makes the pair useful for checking whether the learned representation preserves or ignores one specific difference.

The randomized context of an anchor is kept deliberately small at every corpus level. Anchor families are not required to satisfy the size, depth, and activity thresholds used for ordinary families. Consequently, \texttt{simple}, \texttt{medium}, and \texttt{complex} identify the corpus in which an anchor occurs; they do not necessarily describe the size of the anchor itself. Keeping the anchors small and stable allows the same diagnostic contrast to be repeated while the ordinary families become larger and deeper.

The corpus uses three controlled motifs:
\begin{itemize}
\item The \emph{duplicate-prefix motif} compares a realization that repeats the same visible transition on two branches with one that shares the transition and uses silent routing afterward. The internal structures differ, but the visible traces and recorded partial order agree. The pair tests whether the representation can ignore an irrelevant routing difference.
\item The \emph{concurrency/interleaving motif} compares two activities executed in parallel with an explicit choice between their two sequential orders. The complete visible trace language is the same, but the recorded partial order differs. The pair tests whether the representation retains information about concurrency instead of relying on traces alone.
\item The \emph{M-pattern motif} compares a block-structured target with a Petri net containing non-free-choice routing. The accepted surrounding context preserves the certified visible-language and recorded partial-order relation. The pair tests whether related behavior can be recognized across a larger structural difference, without claiming equivalence outside that accepted context.
\end{itemize}

\subsection{Relation records and event log observations}\label{sec:relations}

Each behavior family contains two Petri net realizations of the designated process tree. For example, the duplicate-prefix family contains one Petri net with repeated visible transitions and another with a shared transition followed by silent routing. Merely placing these two Petri nets in the same family is not enough to determine how they should supervise the neural system. The dataset must first answer two questions: \emph{what behavioral relationship do the Petri nets have}, and \emph{how confidently was that relationship established}? These questions are different. Two Petri nets may produce the same visible traces but represent different concurrency, and a search that finds matching traces up to a resource limit does not prove that their complete languages are equal.

For this reason, the pair of Petri net realizations receives a \emph{relation record} before event logs are sampled. The record keeps three fields separate:
\begin{itemize}
\item \emph{Evidence} describes how the relationship was established, such as complete state-space exploration or a structure-preserving construction.
\item \emph{Semantics} describes what is known to agree: the complete visible trace language, the recorded partial-order class, both, or neither.
\item \emph{Training role} states how the pair may be used, for example as a strong positive, as a weaker ordering example, or not as an exact positive.
\end{itemize}
This separation prevents the method used to examine a pair from being confused with the behavioral claim supported by that examination. Table~\ref{tab:relation-evidence} summarizes the available evidence types.

Only after the model relationship has been recorded does the generator construct event log observations. It first creates a finite \emph{trace pool} from which logs can be sampled. For a non-looping family, complete state-space exploration provides this pool when both Petri net searches terminate. If a search reaches a safeguard, its collected traces remain bounded evidence and are not treated as the complete language.

Looping models need a different procedure because their visible language may be infinite. For ordinary looping families, isomorphic construction certifies the relationship between the Petri nets. The generator then performs seeded playout, removes duplicate traces, and sorts the result to create a finite sampling pool. This pool is used only to create observations; it is not claimed to enumerate the infinite language. Keeping \emph{relation evidence} separate from the \emph{observation source} prevents a finite sample from being mistaken for a proof of model equivalence.

Two event logs are drawn from the resulting trace pool, with the same configured number of traces. The \emph{cycled-coverage observation}, implemented as \texttt{uniform\_variants}, visits the retained variants in a fixed cycle before shuffling them. Its purpose is to give broad and relatively balanced coverage of the available pool. If the pool is larger than the event log capacity, only a deterministic subset can be included; coverage therefore refers to the retained subset, not necessarily to the model's complete language.

The \emph{independently resampled observation} draws traces with replacement. It may repeat some variants many times and omit others, even though it uses the same source pool as the coverage-oriented observation. The two logs can therefore have different empirical frequencies without representing different underlying behavior. Presenting both views teaches the model to separate sampling variation from behavioral variation.

The stored event logs themselves remain clean. Noise and incompleteness are introduced only as training-time augmentation, rather than being written into the evaluation data. This keeps the quantitative evaluation tied to known, reproducible observations.

Finally, each observation creates a \emph{first-seen activity mapping}. Activities receive neutral names in the order in which they first appear. In the request example, an observation that encounters \textsf{accept} before \textsf{reject} may map them to $A_1$ and $A_2$; an observation encountering them in the opposite order may reverse those names. Activities absent from the finite log are appended in a stable order obtained from the process tree and trace pool.

For each observation, the same activity mapping is applied to the event log, the process tree, and both Petri nets. Their activity names therefore agree within each stored row. A different observation may assign different neutral names to the same underlying activities. Activity names alone consequently cannot determine whether two artifacts are related; training uses the stored relation record instead.

\subsection{Generator implementation and relation checks}\label{sec:generation}

The generator must satisfy two requirements. First, it must be \emph{reproducible}: using the same configuration and seed must recreate the same families. Second, it must produce \emph{trustworthy supervision}: every retained family must contain usable process models, and every claimed behavioral relationship must be supported by the recorded evidence. Randomly producing artifacts without these checks could introduce invalid Petri nets or label uncertain pairs as equivalent.

Reproducibility is more subtle than assigning one global random seed. Family construction contains several random decisions: sampling the process structure, creating a representation variant, simulating traces, forming event log observations, and applying augmentation. If all decisions shared one random sequence, changing the number of random draws in one stage could change the outcomes of later stages. The implementation therefore derives a separate, family-specific random stream for each purpose from the global seed using BLAKE2b. This keeps the random components independent while allowing the complete dataset to be recreated.

Algorithm~\ref{alg:generation} presents the construction in execution order. Each loop iteration attempts to create one family. A candidate is retained only after its process tree, Petri nets, behavioral evidence, event logs, and activity mappings have been constructed and checked. If a required check fails, the candidate is discarded and a new attempt begins. The algorithm is kept compact; the paragraphs after it explain the main checks and their consequences.

\begin{algorithm}[H]
\centering
\caption{Behavior-family generation}
\label{alg:generation}
\begin{algorithmic}[1]
\Require complexity profile $c$, family target $n$, deterministic seed $s$
\State initialize split-local family list $\mathcal{F}\leftarrow\varnothing$
\State allocate controlled-motif and ordinary-root quotas
\While{$|\mathcal{F}|<n$}
  \State derive family-specific random streams from $s$
  \State sample an ordinary process tree under $c$ or place a controlled motif in a shared context
  \State construct paired Petri net realizations $N^{(1)},N^{(2)}$
  \State reject failed conversion, reachability, or dead-transition checks
  \If{$T$ is an ordinary looping process tree}
    \State record construction isomorphism and simulate a seeded trace pool
  \Else
    \State enumerate each visible language under the configured safeguards
    \State reject empty or unequal collected languages
    \State record exact evidence if both searches finish; bounded evidence otherwise
  \EndIf
  \State construct cycled-coverage and independently resampled event log observations
  \State apply each first-seen map and flatten two realization variants by two event log observations
  \State store relation metadata, targets, seeds, and four rows
\EndWhile
\State verify coverage constraints and commit the split
\end{algorithmic}
\end{algorithm}

The first checks concern \emph{model validity}. Both Petri net realizations must be constructed successfully, their final markings must be reachable, and they must contain no dead transitions. A family that fails any of these checks is rejected. This prevents the relation analysis from comparing models that cannot execute as intended.

The next checks concern \emph{behavioral evidence}. For a non-looping family, the implementation explores the reachable markings of both Petri nets and collects their visible traces. Exploration is stopped if it visits 5,000 states, completes 10,000 traces, reaches visible length 32, or triggers the safeguard for silent transitions. These limits prevent a difficult candidate from consuming unbounded time or memory.

The result of exploration determines the relation certificate. If both searches finish and return the same complete visible language, the evidence is \emph{exact}. If a safeguard stops either search, any agreement applies only to the traces collected so far and the evidence is \emph{bounded}. For ordinary looping families, where exhaustive enumeration may be impossible, a structure-preserving construction provides an \emph{isomorphic} certificate instead.

The training split retains only families with exact or isomorphic certificates. A candidate with bounded evidence is rejected and replaced because it cannot support an exact positive relation. Validation and test splits may retain bounded-evidence families, but such families are never interpreted as exact visible-language positives. The fixed evaluation subset happens to contain no bounded cases: the \texttt{simple} subset contains 14 exact and two isomorphic families, while the \texttt{medium} and \texttt{complex} subsets each contain 12 exact and four isomorphic families.

Finally, the generator checks \emph{corpus coverage}. It verifies the required motif quotas and confirms that each controlled motif occurs in both Petri net realization positions. Once a family passes all checks, its relation certificate is copied into every stored row. Training can then use the recorded certificate directly instead of trying to reconstruct behavioral relationships from activity labels or surface structure.

\subsection{Cross-artifact architecture}\label{sec:architecture}

The main architectural challenge is that the same artifacts must support two tasks with different information needs. For \emph{retrieval}, the system must compare complete artifacts quickly, even when one is an event log and another is a process tree or Petri net. A single compact vector is suitable for this comparison. For \emph{candidate generation}, however, the decoder must recover local details such as activities, ordering information, relations between parents and children, and graph neighborhoods. Compressing everything into one vector would make these details difficult to access.

\model therefore gives every artifact encoder the same two-part output. The first part is a \emph{semantic vector} $\vect z_m$: a normalized, fixed-size summary used to compare artifacts in the shared space. The second part is a \emph{contextual memory} $H_m$: a collection of source states that preserves the finer information needed by the process tree decoder. The encoders produce these outputs in a common form, although they read different input structures.

Figure~\ref{fig:architecture} shows how the two outputs are used. The \emph{semantic path} compares the vectors $\vect z_m$ for retrieval and behavioral ordering. The \emph{direct-generation path} lets the decoder attend to the contextual memory $H_m$ of one source artifact. The \emph{fusion path} supports several source artifacts: their semantic vectors are averaged, and the result is projected back into a decoder memory. All generation paths lead to the same process tree decoder and therefore to the same output format.

The process tree encoder and decoder use Transformer attention \cite{Vaswani2017}; the event log encoder uses recurrent states within traces and set attention across traces \cite{Lee2019}; and the Petri net encoder exchanges messages along typed arcs. \subsection{Grammar-Constrained Candidate Decoder and Structural Guarantees}\label{sec:decoder-guarantees}

Candidate generation is useful only if its output is a valid process model. An ordinary token decoder does not provide this guarantee. It may stop while an operator is still missing a child, produce an activity when an operator arity is required, or otherwise return a token sequence that cannot be parsed as a process tree. Rejecting such sequences only after decoding would waste search effort and could leave the analyst without any usable candidate. The decoder therefore applies the process tree grammar while it generates the sequence.

The need for this constraint is easiest to see in prefix notation. After the decoder emits a two-child sequence operator, it must generate exactly two complete child subtrees before it may close that part of the expression. Ending after the first child would produce an incomplete tree. Conversely, once all required children have been supplied, another child cannot be added to that operator. These requirements are determined by the grammar, so they need not be learned from examples.

To enforce them, the shared decoder works together with a small grammar controller. The neural decoder proposes the process tree structure, operator arities, and visible activities; its copy component can reuse activities stored in the source memory. At every step, the controller records whether an arity is expected and how many child positions remain open. It then masks every token that is illegal in the current state. End-of-sequence becomes available only when no child position remains open. If ordinary search reaches its budget first, a deterministic completion rule fills the outstanding positions and closes the expression, provided that the completion budget is sufficient.

\input{figures/decoder}

Two additional masks control visible activities. The \emph{source-alphabet mask} prevents the decoder from introducing an activity that is absent from the permitted source alphabet. In the synthetic evaluation, a separate policy also suppresses repeated visible labels. Repeated labels can be legitimate in real processes, so the external event log cases are evaluated both with and without that repeated-label restriction.

These constraints have a deliberately limited purpose. They ensure that a completed output is well formed, uses only permitted activities when the corresponding mask is enabled, and can be converted from a process tree to a Petri net. They do not tell the decoder which valid tree best represents the source. The decoder must still learn the appropriate operators, activity positions, tree size, and control-flow behavior. A grammar-valid candidate can therefore be behaviorally wrong. The following propositions state precisely what is and is not guaranteed.

\begin{Proposition}[Grammar-mask validity]
Let $p$ be a decoder prefix whose maintained grammar state is valid. If the next token is selected only from the mask induced by that state, then the extended prefix does not violate the arity and token-type rules in Eq.~\eqref{eq:grammar}.
\end{Proposition}
\begin{proof}[Proof sketch]
The controller records the token type expected next and the number of open child positions. Its mask admits exactly the tokens allowed in that state. Therefore, adding an admitted token preserves validity. Repeating this argument for each decoding step proves the claim.
\end{proof}

\begin{Proposition}[Deterministic completion]
Assume a valid prefix, at least one permitted terminal token, and a completion budget sufficient to fill every open slot and emit end-of-sequence. The deterministic completion rule returns a closed expression in the grammar.
\end{Proposition}
\begin{proof}[Proof sketch]
The completion rule first supplies any pending arity and then fills open child positions without introducing another unfinished operator. Each such step reduces the remaining work. Because the completion budget is assumed to be sufficient, the number of open positions eventually reaches zero and end-of-sequence becomes legal.
\end{proof}

\begin{Proposition}[Source-alphabet restriction]
When the source-alphabet mask is enabled, every visible activity in a completed output belongs to the permitted source alphabet.
\end{Proposition}
\begin{proof}[Proof sketch]
Every activity token outside the permitted alphabet is masked at every step. The remaining structural tokens and $\tauact$ introduce no visible activity. Hence every visible activity in the completed output belongs to the permitted alphabet.
\end{proof}

\begin{Proposition}[Structural guarantees do not imply behavioral equivalence]
Grammar validity, source-alphabet compliance, and process tree-to-Petri net convertibility do not jointly imply visible-language or partial-order equivalence to the source.
\end{Proposition}
\begin{proof}[Proof sketch]
For permitted activities $A$ and $B$, both $\mathsf{SEQ}(A,B)$ and $\mathsf{XOR}(A,B)$ are valid, alphabet-compliant, and convertible. However, the first requires both activities in order, while the second chooses one of them, so their visible languages differ. Similarly, a parallel composition and a choice between its serial orders can agree on complete visible traces while representing different partial-order behavior.
\end{proof}

\begin{Proposition}[Representational convertibility]
Every completed expression accepted by the grammar in Eq.~\eqref{eq:grammar} denotes a block-structured process tree and therefore admits the standard process tree to Petri net construction used by the implementation.
\end{Proposition}
\begin{proof}[Proof sketch]
The grammar contains only visible or silent leaves and the sequence, exclusive-choice, parallel, and two-child loop constructors. The standard conversion creates a Petri net fragment for each leaf and recursively combines those fragments for each constructor \cite{vanDerAalst2016}. It therefore converts every completed grammar expression. This result concerns convertibility only; it does not establish agreement with the source artifact.
\end{proof}

In summary, grammar masking prevents malformed prefixes, deterministic completion can close an unfinished valid prefix under the stated assumptions, and the resulting block-structured process tree supports the standard sound Petri net conversion. These are \emph{structural guarantees}. Whether the candidate reproduces the behavior of its source is a separate empirical question, evaluated with the behavioral measures described in Section~\ref{sec:setting}.

\subsection{Computational Cost}\label{sec:complexity}

Computational cost matters because the system performs three different operations: it encodes process artifacts, searches a repository of stored representations, and generates process tree candidates. These operations scale with different properties of the input. The following analysis therefore describes them separately. It gives asymptotic costs, which explain how the required work grows, rather than measured execution times.

\emph{Encoding cost} depends on the structure of the source artifact. Let $d_h$ denote the encoder hidden dimension. For an event log containing $E_L$ presented events in $R$ traces, the recurrent trace encoder costs $O(E_Ld_h^2)$, followed by set aggregation over the $R$ trace representations. For a process tree containing $n_T$ tokens, the full-attention term costs $O(n_T^2d_h)$ because every token can attend to every other token. For a Petri net with $V_N$ nodes and $E_N$ arcs, $k$ message-passing steps cost $O\!\left(k(V_Nd_h^2+E_Nd_h)\right)$. These expressions ignore fixed numbers of encoder layers.

\emph{Retrieval cost} is incurred after the repository artifacts have been encoded and their semantic vectors have been stored. Let $M$ be the number of stored artifacts and $d_z$ the semantic-vector dimension. An exact query compares the query vector with all $M$ stored vectors, requiring $O(Md_z)$ work and $O(Md_z)$ storage for the collection. An approximate index could reduce query time at the cost of additional approximation and index-management choices, but approximate retrieval is not evaluated in this study.

\emph{Generation cost} depends mainly on how many candidate prefixes the decoder explores and how long they become. With beam width $B$ and generated length $G$, beam search performs $O(BG)$ decoder steps. Each step also attends to the fixed source memory and computes a projection over the output vocabulary. The grammar mask restricts the legal choices but does not remove these decoder operations.

The selected checkpoint contains 6,263,248 trainable parameters. This number describes model size, not observed speed. The experimental protocol does not measure encoding latency, repository query time, decoding latency, or peak memory. Consequently, the study reports the analytical costs above but makes no empirical scalability claim.

\subsection{Training objectives}\label{sec:training}

Training must make both parts of the architecture useful at the same time. The decoder must generate the designated process tree from any supported input, while the encoders must place behaviorally related artifacts near one another in the shared semantic space. Training only for reconstruction would not ensure useful cross-artifact comparisons. Training only for alignment would not teach the decoder to produce a process model.

The objective therefore combines three kinds of learning signal. \emph{Reconstruction signals} teach candidate generation from individual artifacts and from fused inputs. \emph{Relation signals} organize the shared space by distinguishing exact behavioral agreement, weaker forms of similarity, and unrelated behavior. \emph{Regularization signals} prevent the semantic vectors from collapsing to nearly the same point.

Not every artifact pair supports the same conclusion. For example, two artifacts with the same strong-behavior and partial-order identifiers can be treated as a strong positive pair. Two artifacts that agree only on visible traces should be kept closer than unrelated artifacts, but they should not be forced to have identical vectors. Likewise, two finite event log observations drawn from the same source should remain close even when their sampled traces and frequencies differ. The relation records produced by the generator specify which learning signals are justified for each example. Table~\ref{tab:data-to-loss} summarizes this connection.

The reconstruction part has two roles. $\mathcal{L}_{\mathrm{recon}}$ combines the direct reconstruction losses that decode the designated process tree from each individual artifact type. $\mathcal{L}_{\mathrm{fuse}}$ applies the same target to generation conditioned on several fused artifacts.

Four terms organize the semantic space. $\mathcal{L}_{\mathrm{exact}}$ pulls together pairs that agree under both recorded semantics. $\mathcal{L}_{\mathrm{hier}}$ handles visible-language agreement without partial-order agreement: it places such pairs closer than unrelated artifacts without forcing them to the same point. $\mathcal{L}_{\mathrm{obs}}$ aligns alternative finite event log observations from the same source pool. Finally, $\mathcal{L}_{\mathrm{geom}}$ encourages distances between semantic vectors to follow the experiment-specific behavioral distance.

The remaining term, $\mathcal{L}_{\mathrm{reg}}$, maintains variation across representation dimensions and discourages redundant dimensions. Its purpose is to keep the shared space informative rather than allowing many artifacts to receive almost identical vectors. The complete objective is
\begin{align}
\mathcal{L}={}&
 \mathcal{L}_{\mathrm{recon}}
 +\mathcal{L}_{\mathrm{fuse}}
 +\mathcal{L}_{\mathrm{exact}}
 +\mathcal{L}_{\mathrm{hier}}
 +\mathcal{L}_{\mathrm{obs}}
 +\mathcal{L}_{\mathrm{geom}}
 +\mathcal{L}_{\mathrm{reg}}.
\label{eq:objective}
\end{align}
Equation~\eqref{eq:objective} uses compact notation in which each component includes its configured coefficient. The three direct reconstruction losses and the fused-input reconstruction loss each have weight 1.00. Exact cross-artifact alignment has weight 0.30. Hierarchical ordering and observation consistency each have weight 0.15, and soft behavioral geometry has weight 0.25. These values keep reconstruction as the principal signal while still shaping the shared representation.

The semantic vectors are deterministic outputs of the encoders; they are not samples from a learned probability distribution. A Kullback-Leibler regularizer is therefore not applicable, and its configured coefficient is zero.

\subsection{Curriculum learning and checkpoint selection}\label{sec:curriculum}

Training begins with a bootstrapping problem. The neural system must learn cross-artifact alignment, activity correspondence, and autoregressive process tree grammar at the same time. Starting immediately with the largest process trees couples these tasks strongly: an incorrect operator or arity changes the number of open child slots and can invalidate the interpretation of every subsequent token. The curriculum is therefore intended to establish closure, copying, and basic alignment on short process trees before introducing deeper structures. Easier rehearsal batches remain active to limit forgetting, while controlled motifs provide stable representation anchors at every level. The study does not include a retrained no-curriculum ablation, so these are design motivations rather than causal findings.

The implementation distinguishes three terms. A \emph{complexity profile} specifies the ordinary process tree generator bounds. A \emph{complexity corpus}, or level, is an independently generated \texttt{simple}, \texttt{medium}, or \texttt{complex} dataset. A \emph{curriculum stage} specifies the mixture of those corpora currently used for training. Curriculum learning is the competence-gated transition between these stage mixtures.

\subsection{Fixed evaluation subset}\label{sec:fixed-evaluation}

The detailed evaluation is substantially more expensive than computing a loss or an embedding. For every evaluated input, beam decoding explores several candidate process trees. The resulting models are then executed to obtain traces for behavioral comparison, and the process discovery experiment constructs and evaluates an additional model from each event log. Repeating all of these operations for the complete test split at all three complexity levels would require a multi-hour run. A smaller, fixed subset makes the evaluation reproducible and keeps every method compared on exactly the same cases.

The selection unit is the \emph{behavior family} defined in Section~\ref{sec:corpus}. Each family is stored as four rows containing every pairing of its two Petri net realizations and two event log observations. A subset is \emph{family-complete} when selecting a family retains all four of these rows. This is necessary because the evaluation compares alternative realizations and observations; selecting individual rows would break those comparisons and would incorrectly treat related rows as independent cases.

The full test split contains 512 families at each of the \texttt{simple}, \texttt{medium}, and \texttt{complex} levels. Within each level, families are grouped into \emph{strata}. A stratum is a group with the same structural-motif category and observation category. The ordinary and controlled motif categories were introduced in Section~\ref{sec:anchor-families}, and the coverage-oriented and independently sampled observations were introduced in Section~\ref{sec:setting}. The deterministic selector cycles through these strata in a fixed order. It does not use model scores, decoding quality, or any test result when choosing families. This procedure retains representation of the designed data categories without making the subset performance-dependent.

The selector retains 16 complete families per level, giving 48 families in total. Because every family contributes four rows, the subset contains 192 stored rows. Each row is decoded under the four source conditions described in Section~\ref{sec:architecture}: process tree input, event log input, Petri net input, and fused input. The detailed evaluation therefore contains $192\times4=768$ decoding runs. Unless a result is explicitly described as a full-corpus statistic, it refers to this fixed subset rather than to all 1,536 test families.

The evaluation needs two complementary ways to compare a generated process tree with its reference. The first measures \emph{structural difference}. The ordered process tree edit cost is the minimum cost of inserting, deleting, or relabeling nodes to transform one folded process tree into the other. Folding was defined in Section~\ref{sec:anchor-families}. Dividing this cost by the size of the larger tree produces the \emph{normalized process tree edit distance}, which makes comparisons across differently sized trees more meaningful. A value of zero means that the folded trees are identical.

Structural distance alone is insufficient because different process structures can describe similar behavior. The evaluation therefore also uses a common, computationally tractable \emph{behavior distance}, denoted $d_B$. For each family or decoded output, the available traces are converted into three empirical distributions. The trace-variant distribution $p_{\mathrm{var}}$ records the relative frequency of each complete activity sequence. The boundary-aware directly-follows distribution $p_{\mathrm{df}}$ records adjacent activity pairs after adding explicit start and end markers. The trace-length distribution $p_{\mathrm{len}}$ records the relative frequency of each trace length. Each distribution is normalized so that its values sum to one.

For two evaluated objects $f$ and $g$, $d_B$ averages the differences between their three distributions:
\begin{equation}
d_B(f,g)=\frac{1}{3}\left(
 \lVert p_{\mathrm{var}}^f-p_{\mathrm{var}}^g\rVert_1+
 \lVert p_{\mathrm{df}}^f-p_{\mathrm{df}}^g\rVert_1+
 \lVert p_{\mathrm{len}}^f-p_{\mathrm{len}}^g\rVert_1
\right),
\label{eq:behavior-distance}
\end{equation}
Here, $\lVert p-q\rVert_1$ is the sum of the absolute differences between corresponding distribution values. For normalized distributions, each component ranges from zero to two. Consequently, $d_B=0$ means that the three measured summaries are identical, while larger values indicate greater disagreement; the maximum is two.

This distance is intentionally an \emph{experiment-specific summary}, not a complete semantic equivalence test. It can miss differences that do not change the three distributions, including some causal or concurrency distinctions. Moreover, related behavioral descriptors contributed to training. Agreement with $d_B$ therefore shows that a representation preserves this particular behavioral ordering; it does not prove visible-language or partial-order equivalence.

Finally, the reported intervals describe uncertainty among the selected families. A \emph{family-level bootstrap} repeatedly draws complete families with replacement, retaining all rows and results belonging to each drawn family, and recomputes the metric \cite{Efron1994}. Each resample contains the same number of families as the evaluation set used for that metric: 16 for a level-specific result, or 48 for a result pooled across all levels. The stated percentile interval contains the central 95\% of these recomputed values. Resampling families rather than rows respects the dependence among the four rows of one family. These intervals capture variation within the selected subset only; they do not include uncertainty from generating another corpus, changing the training seed, retraining the model, or selecting another checkpoint.

\subsection{RQ-aligned metrics and baselines}\label{sec:rq-metrics}

Each research question evaluates a different capability, so no single score is sufficient. Representation metrics ask whether related artifacts occupy useful neighborhoods, retrieval metrics ask whether relevant artifacts appear early in a ranked list, and generation metrics ask whether a decoded process tree is structurally and behaviorally close to its reference. Table~\ref{tab:rq-metrics} summarizes these evaluation units, metrics, and baselines.

\emph{Shared similarity and relevance definitions.} Because every semantic vector is normalized, the cosine similarity of two artifacts is $\vect z_i^{\mathsf T}\vect z_j$. It ranges from $-1$ to $1$, and larger values mean that the vectors point in more similar directions. Cosine distance is $1-\vect z_i^{\mathsf T}\vect z_j$, so smaller values mean greater similarity. For retrieval, a candidate is relevant when it shares the strongest certified behavior identifier available for the query, implemented as \texttt{strong\_behavior\_id} or, when that field is absent, \texttt{exact\_behavior\_id}. In the fixed subset, each relevance group is exactly one selected family and contains its four stored rows.

\emph{\RQone: representation alignment.} \emph{Within-family cosine} is the mean similarity between alternative observations or realizations of the same family; higher is better. \emph{Between-family cosine} is the mean similarity between artifacts from different families; lower values indicate stronger separation. The \emph{nearest-neighbor margin} is the similarity of the nearest same-family artifact minus the similarity of the nearest different-family artifact; a positive, larger margin is better. \emph{Family Recall@1} is the fraction of queries whose single nearest neighbor belongs to the same family. Finally, \emph{Spearman $\rho$} measures whether pairwise cosine distances and the behavior distance $d_B$ rank family pairs in the same order. It ranges from $-1$ to $1$: larger positive values indicate stronger agreement, while zero indicates no monotonic association. The deterministic event log baselines encode trace variants, adjacent activity pairs, eventually-follows pairs in which one activity occurs later but not necessarily immediately, activity frequencies, or aggregate log statistics. The Petri net baselines use either structural counts or a Node2Vec-style representation of graph neighborhoods \cite{Grover2016}.

\emph{\RQtwo: cross-artifact retrieval.} \emph{Recall@1} is the fraction of queries for which the top-ranked candidate is relevant. \emph{Mean reciprocal rank (MRR)} uses $1/r$, where $r$ is the rank of the first relevant candidate, and averages this value over queries. Both metrics range from zero to one, and higher is better; MRR gives partial credit when the first relevant result appears below rank one. The balanced row-level candidate set contains 16 equally represented relevance groups per level, so random group-level Recall@1 is $1/16=0.0625$. Multiple relevant rows make this protocol easier than a deduplicated candidate set, and deterministic tie order can affect MRR; the claims are therefore limited to the stated row-level setting.

\emph{\RQthree: candidate generation and process discovery.} \emph{Exact match} is the fraction of decoded process trees that equal the reference after parsing and semantic folding. Section~\ref{sec:fixed-evaluation} defines the \emph{normalized process tree edit distance}, which measures structural change, and $d_B$, which compares sampled behavior; both are lower when the candidate is closer to the reference. \emph{Behavioral-simulation coverage}, reported as \emph{evaluable}, is the fraction of decoded candidates for which trace simulation completes. Reported behavioral-distance means are conditional on that success, so coverage must be read with the distance.

For event-log input, \emph{footprint fitness} measures how much of the log's observed directly-follows, parallel, start, and end behavior is admitted by the generated process tree. \emph{Footprint precision} measures how much behavior admitted by the tree is also supported by the log. \emph{F1} is their harmonic mean and is high only when both are high. These scores range from zero to one, and higher is better. \emph{Footprint evaluator coverage} is the fraction of cases for which this comparison completes; it is different from behavioral-simulation coverage. These are footprint-based measures, not alignment-based conformance checking scores, and values from different conformance definitions should not be compared directly. Inductive Miner is the specialized process discovery baseline for this experiment. Grammar validity is omitted as a learned metric because the decoder enforces it by construction.

\section{Application Scenario and Reference Implementation}\label{sec:reproduction}

The model is useful in practice only if its output can be \emph{inspected, reproduced, and challenged}. A similarity score alone is not enough: an analyst must be able to see which artifact was encoded, which checkpoint produced the representation, why a result was retrieved, and whether a generated model passes independent checks. This section therefore presents the application scenario together with the reference implementation that supports it.

\subsection{From an input artifact to an analyst decision}

Figure~\ref{fig:application-workflow} summarizes the intended workflow. The starting point may be an XES event log, a PTML process tree, or a marked PNML Petri net. The system validates and canonicalizes the input, applies the corresponding encoder, and places the resulting vector in the shared representation space. The analyst can then use that vector in two complementary ways.

The first and safest use is \emph{cross-artifact retrieval}. The system compares the query vector with stored vectors and ranks repository items by cosine similarity. A high cosine value means that two artifacts are close according to the learned representation; it does \emph{not} prove that they are behaviorally equivalent. The ranked items should therefore be read as useful precedents to inspect, such as an existing Petri net that may explain an incoming event log, rather than as automatically accepted answers. Recall@1 and MRR evaluate this ranking offline when the relevant repository items are known: Recall@1 asks whether the first item is relevant, while MRR also gives credit when the first relevant item appears slightly lower in the list. Neither number is a confidence score for one new, unlabeled query.

The second use is \emph{candidate generation}. If no retrieved model is suitable, the analyst may ask the constrained decoder to propose a process tree from the query representation. The grammar guarantees that the token sequence forms a well-structured tree, but syntactic validity is only the first gate. The candidate must still be converted, simulated, and compared with the available evidence. With a reference tree, exact match and normalized tree-edit distance measure structural agreement. With reference traces, the behavior distance $d_B$ measures sampled behavioral disagreement. With an event log, fitness measures how much observed behavior the candidate admits, precision measures how much candidate behavior is supported by the log, and F1 balances the two. Evaluator coverage states how often those checks could actually be completed. The formal definitions and aggregation units are given in Sections~\ref{sec:fixed-evaluation} and~\ref{sec:rq-metrics}.

\input{figures/workflow}

Retrieval and generation both end with the same decision point: the analyst accepts, rejects, or refines a model only after conformance checking, soundness checks, and behavioral inspection. This separation is deliberate. Dataset-level measures such as Recall@1, MRR, and Spearman $\rho$ describe the evaluated system as a whole; they must not be presented as guarantees about a single production result.

\subsection{Implementation and access}

The open-source implementation is available in the public \href{https://github.com/fit-alessandro-berti/proc-rosetta}{ProcRosetta repository}. An installation-free browser interface is available at \href{https://rosetta-pm.app}{rosetta-pm.app}. The implementation separates artifact input and preprocessing, the three artifact-specific encoders, grammar-constrained decoding, behavioral evaluation, and presentation. The command-line programs and the browser interface call the same inference services and load the same checkpoint format. The browser is therefore an inspection and execution layer over the evaluated implementation, not a separate demonstration model.

On import, the implementation parses and validates the source artifact, records preprocessing warnings, and creates the first-seen canonical activity map described in Section~\ref{sec:relations}. It also checks the artifact against the selected checkpoint's vocabulary and size limits before computing a representation. The session workspace retains the source artifact, canonical map, checkpoint identity, embedding, decoding settings, and validation results. Cache keys depend on both content and configuration, which prevents an embedding or decode produced under one checkpoint or policy from being silently reused under another.

The browser application can be started locally with Streamlit or with the supplied Docker Compose configuration. The container runs as an unprivileged user behind an NGINX reverse proxy. Checkpoints are selected from a server-controlled directory because PyTorch checkpoint files must be treated as trusted executable content; arbitrary checkpoint upload is therefore disabled in the browser.

\section{Results}\label{sec:results}

\subsection{Dataset Integrity and Evaluation Protocol}

The held-out split contains 1,536 families across the three curricula, while the reported quantitative evidence uses the deterministic, family-complete 48-family subset described in Section~\ref{sec:fixed-evaluation}. Alternative rows from a family never cross split boundaries. Independently generated families were not globally deduplicated, so the present split is family-disjoint but not certified behavior-disjoint.
The evaluation retains repeated observations and realizations within each family. Consequently, the reported retrieval results characterize the balanced multi-observation protocol only; they do not establish performance for a deduplicated process repository or a behavior-disjoint split.

\subsection{\RQone: Representation alignment and behavioral ordering}

\RQone{} asks whether the shared representation has two properties at the same time. First, it should be \emph{stable}: different observations or realizations of the same behavior family should remain close. Second, it should be \emph{behaviorally sensitive}: families with more different behavior should be placed farther apart. Both properties are necessary. A representation that maps everything to almost the same point would be stable but useless for comparison, while a representation that separates every input could incorrectly treat two observations of the same process as unrelated.

We examine these properties separately on the fixed evaluation subset. Behavioral sensitivity is evaluated by asking whether distances in the learned space order family pairs in the same way as the experiment-specific behavior distance $d_B$. Stability is evaluated by comparing alternative observations and realizations within each artifact type. The results support both properties under the evaluated protocol: the fused representation follows the ordering induced by $d_B$, especially for the \texttt{medium} and \texttt{complex} families, and every within-type query has a nearest neighbor from the same family. The following paragraphs explain these two results in detail.

\paragraph{Behavioral ordering.}
For every pair of behavior families, the evaluation compares two quantities: the distance between their representations and their behavioral distance $d_B$. Spearman $\rho$ measures whether these quantities produce a similar ranking of family pairs. For example, if $d_B$ indicates that family $F_1$ is behaviorally closer to $F_2$ than to $F_3$, a well-ordered representation should also place $F_1$ closer to $F_2$. Spearman $\rho$ evaluates this relative order; it does not require the representation distance and $d_B$ to have the same numerical scale.

The direction of this metric is important: \emph{a higher positive Spearman $\rho$ is better}. The value ranges from $-1$ to $1$. A value of $1$ means that representation distance and $d_B$ rank all evaluated family pairs in exactly the same order. A value near $0$ means that there is no consistent monotonic ordering between them. A negative value is undesirable here because it means that pairs judged more different by $d_B$ tend to be placed closer together by the representation. Thus, 0.791 indicates stronger agreement than 0.743, and both indicate stronger agreement than 0.577.

Table~\ref{tab:geometry} reports this comparison. For the fused representation, Spearman $\rho$ increases from 0.577 on \texttt{simple} families to 0.743 on \texttt{medium} families and 0.791 on \texttt{complex} families. Because higher positive values are better, this increase means that agreement with $d_B$ becomes stronger across the three evaluated levels. All three correlations are positive, so larger behavioral differences generally correspond to larger distances in the learned space.

\paragraph{Interpretation.}
Taken together, the results support RQ1 within the stated synthetic evaluation setting. Alternative observations and realizations remain close to their families, while distances between families reflect the ordering defined by $d_B$. This makes the representation suitable for neighborhood inspection and motivates the cross-artifact retrieval experiment in RQ2.

The conclusion is deliberately limited. First, $d_B$ summarizes trace variants, directly-follows relations, and trace lengths; it is not a complete test of visible-language or partial-order equivalence. Second, related components of $d_B$ also contribute to the training descriptor. The reported correlation therefore shows that the model learned the intended experiment-specific behavioral ordering, not that it discovered a universal process-semantic distance. The retrieval results below and the footprint-based conformance results provide complementary evidence because they do not reuse this exact scalar target.

\FloatBarrier
\subsection{\RQtwo: Cross-Artifact Retrieval}\label{sec:retrieval-results}

Process repositories rarely contain only one artifact type. An analyst may have an event log but need an existing process tree, or may have a Petri net and want to find related logs. Ordinary repository search cannot directly compare these artifacts because their structures are different. \RQtwo{} therefore asks whether the shared representation can support \emph{cross-artifact retrieval}: using one artifact type as a query to rank artifacts of another type.

\paragraph{Retrieval setting.}
The evaluation considers all six ordered directions among event logs, Petri nets, and process trees. For example, event log $\rightarrow$ process tree means that an event log is the query and only process tree representations are searched. Reversing the arrow creates a different task: process tree $\rightarrow$ event log uses a process tree as the query and searches only event logs.

A candidate is relevant when it belongs to the same behavior family as the query. At each complexity level, the candidate set contains 64 stored rows from 16 families. Each family contributes four rows, and all four rows from the query's family are treated as relevant. The experiment is therefore a \emph{multi-observation, row-level retrieval task}. It tests whether related stored representations form a useful neighborhood, not whether the system can retrieve one unique, deduplicated model from a large production repository.

\paragraph{Metrics and their direction.}
Two metrics describe the ranking. \emph{Recall@1} asks a strict question: does the first retrieved row belong to the correct family? It is the fraction of queries for which the answer is yes. Recall@1 ranges from zero to one, and \emph{higher is better}. A value of 1.000 means that every query retrieves a relevant row first; a value of 0.750 means that this happens for three quarters of the queries.

\emph{Mean reciprocal rank (MRR)} also considers where the first relevant row appears when it is not ranked first. If the first relevant row is at rank one, the query receives a score of $1$; at rank two, it receives $1/2$; at rank four, it receives $1/4$. MRR is the average of these scores across all queries. It also ranges from zero to one, and \emph{higher is better}. MRR therefore gives partial credit when a relevant result is near the top, whereas Recall@1 gives credit only when a relevant result is first.

The 16 families are equally represented. A random ranking places one of the four relevant rows first with probability $4/64=1/16=0.0625$. This value is the random Recall@1 baseline. It provides a simple reference point: results substantially above 0.0625 show that the ranking uses information beyond random group selection.

The strongest direction is process tree $\rightarrow$ event log, with Recall@1 of 0.875 and MRR of 0.905 at every complexity level. Process tree $\rightarrow$ Petri net is also strong: Recall@1 increases from 0.812 to 0.875 and MRR increases from 0.867 to 0.908 between the \texttt{simple} level and the two higher levels. These results mean that process tree queries usually place a related model or observation first and, when they do not, a relevant result still tends to appear near the top.

The most difficult direction is event log $\rightarrow$ process tree. Its Recall@1 is 0.656 on the \texttt{simple} and \texttt{medium} families and 0.688 on the \texttt{complex} families. This difficulty is consistent with the information available in the artifacts: an event log contains only finite observed executions, whereas a process tree explicitly describes control-flow structure and may permit behavior absent from the log. The experiment does not isolate this as the only cause, but it explains why this direction is intrinsically less direct.

The direction of retrieval matters. For Petri net $\rightarrow$ event log, Recall@1 increases from 0.703 to 0.828 and MRR increases from 0.755 to 0.855 across the three levels. Event log $\rightarrow$ Petri net, in contrast, remains between 0.72 and 0.75 Recall@1. This asymmetry does not contradict the use of cosine similarity: the similarity of one specific pair is symmetric, but reversing a retrieval task changes which artifacts act as queries and which collection is ranked. The two directions can therefore produce different aggregate results.

Figure~\ref{fig:pca} gives an intuitive view of the cross-artifact neighborhoods behind the numerical results. Each connected set contains the event log, Petri net, and process tree representations of one behavior family. When the three markers are close, the visualization suggests that the encoders place the different artifact types in a similar region of the shared space. This is the relationship needed to retrieve one artifact type by using another as the query.

\paragraph{Interpretation and scope.}
The results support RQ2 under the evaluated protocol: artifacts from the same behavior family can often be retrieved across artifact types, and the first relevant result is usually at or near the top of the ranking. This supports using the shared representation to suggest related artifacts for analyst inspection.

The scope of this conclusion is limited by the candidate set. Each relevance group contains four candidate rows, so a query has several positive observations or realizations that it can retrieve. This makes the task easier than searching a repository containing one deduplicated artifact per process. Equal multiplicity keeps the random family prior at $1/16$, but repeated rows can still affect ranks and the deterministic ordering of ties. The results must therefore be described as \emph{multi-observation retrieval}, not as deduplicated process-level retrieval.

The evaluation also uses a fixed subset generated by the same corpus design as the training data. It does not measure retrieval from a large external repository, and it does not show that the top-ranked artifact is behaviorally equivalent to a new production query. In the intended application, retrieved artifacts remain candidates that require behavioral checking and analyst review.

\subsection{\RQthree: Structural Guarantees and Behavioral Limits of Candidate Generation}\label{sec:decode-results}

\RQthree{} examines candidate generation. The central issue is that two different questions must not be confused. The first is, ``Did the decoder produce a valid process tree?'' The second is, ``Does that tree preserve the behavior of the source artifact?'' The grammar-constrained decoder guarantees the first property, but it must learn the second property from data.

This distinction is easy to see in a small example. The process trees $\rightarrow(A,B)$ and $\times(A,B)$ are both syntactically valid and can both be converted to Petri nets. Their behavior is nevertheless different: the first requires $A$ before $B$, while the second permits either $A$ or $B$. A grammar can prevent missing children, invalid operators, and unfinished trees, but it cannot decide which of these two valid structures describes the source process correctly.

The experiment therefore evaluates every generated tree in two stages. First, it checks the \emph{structural guarantee}. Every decoded sequence must form a closed process tree, use only permitted activity labels, respect operator arity, and convert to a Petri net. These conditions hold for every evaluated output because illegal tokens are masked during decoding. Second, it measures \emph{semantic preservation}: how closely the valid candidate matches the designated reference in structure and sampled behavior.

Candidates are generated from four source conditions. \emph{Process tree} uses the reference tree as input and tests reconstruction. \emph{Event log} uses only finite observed executions. \emph{Petri net} uses the graph representation of a model realization. \emph{Fusion} uses the equal-weight combination of the available artifact representations. All four conditions produce a process tree, so their results can be compared against the same designated target.

\paragraph{Metrics and their direction.}
Table~\ref{tab:decode} reports four quantities. \emph{Evaluable} is the percentage of generated trees for which behavioral simulation finishes successfully. Higher coverage is better, but it only says that a candidate could be evaluated; it does not say that the candidate is behaviorally correct. \emph{Exact} is the percentage of generated trees that equal the folded reference tree. Higher exact-match percentages are better, and 100\% would mean that every designated target was reconstructed exactly.

The remaining columns are distances, so their direction is reversed: \emph{lower is better}. The behavior distance $d_B$ compares the distributions of trace variants, directly-follows relations, and trace lengths. A value of zero means that these measured behavioral summaries agree exactly; larger values mean greater disagreement. The normalized process tree edit distance measures the structural changes needed to transform the candidate into the folded reference tree. It is also zero for an exact structural match and increases as more nodes must be inserted, deleted, or relabeled. Both distances are needed because two trees can differ structurally while exhibiting similar behavior, or look structurally similar while making an important behavioral error.

\paragraph{Results by source artifact.}
Process tree input gives the best overall reconstruction results. This is expected because the source already has the same hierarchical structure as the output. Even in this favorable condition, however, exact match falls from 34.4\% for \texttt{simple} families to 28.1\% for \texttt{medium} families and 15.6\% for \texttt{complex} families. At the same time, $d_B$ increases from 0.861 to 1.105 and tree-edit distance increases from 0.509 to 0.645. Because lower distances are better, both trends show that reconstruction becomes less faithful as process complexity increases.

Event log input is the hardest condition. Its exact-match rate is 0\% at every level, and its behavioral distance increases from 1.169 to 1.291. An event log does not expose an explicit control-flow hierarchy and contains only the executions that happened to be sampled, so the decoder must infer choices, concurrency, loops, and unobserved paths. A zero exact-match rate is not sufficient by itself to prove behavioral failure, because several different process trees may legitimately explain the same finite log. In this experiment, however, the relatively large $d_B$ values show that the differences are not only harmless alternative tree structures.

Petri net input performs between process tree and event log input for exact reconstruction. It reaches 12.5\% exact match on \texttt{simple} families and 6.2\% on the two higher levels. The Petri net contains explicit control-flow structure, but that structure must still be converted from a graph into the hierarchical organization required by a process tree. The edit and behavior distances show that this conversion remains difficult even though every output is grammatically valid.

Equal-weight fusion does not improve on the strongest individual source. It reaches 3.1\% exact match on \texttt{simple} families and 0\% on the other levels, while its $d_B$ is higher than that of the best individual source at every level. This result suggests that a simple average can discard useful source-specific information or give equal influence to sources of unequal reliability. The present experiment evaluates the stated equal-weight policy only; it does not establish that every learned or reliability-aware fusion method would behave in the same way.

Evaluator coverage is close to complete but must still be reported. Most conditions reach 100\%. The exceptions are event log input on \texttt{medium} families, with 96.9\%, and fusion on \texttt{complex} families, with 93.8\%. These missing evaluations arise when a grammar-valid candidate becomes too large for reliable behavioral simulation within the evaluation safeguards. This again illustrates the main distinction of RQ3: a tree may satisfy every structural rule and still be difficult to evaluate or behaviorally unsuitable.

\paragraph{Interpretation and scope.}
The answer to RQ3 is therefore mixed but clear. The grammar constraints provide the promised \emph{structural guarantee}: every decoded output is a closed process tree over the permitted vocabulary and is convertible to a Petri net. They do not provide a \emph{behavior-preservation guarantee}. Exact reconstruction is limited, behavioral disagreement grows with ordinary-family complexity, and equal-weight fusion does not repair the problem.

The decoder should consequently be used as a candidate generator rather than as an automatic translator. Its output is structurally usable, which makes subsequent analysis possible, but the candidate must still undergo conformance checking, soundness analysis, and human inspection before acceptance. The next subsection makes this practical limitation more concrete by comparing event log decoding with a specialized process discovery method.

\subsection{Efficiency and Scalability}

The architecture contains 6,263,248 trainable parameters, and Section~\ref{sec:complexity} gives asymptotic costs for encoding, indexed retrieval, and beam decoding. Empirical encoding latency, repository-indexing time, query latency, peak memory, and beam-decoding latency were not measured in this study. Accordingly, no empirical scalability claim is made.

\section{Discussion}\label{sec:discussion}

The main question is not only whether one model can read event logs, process trees, and Petri nets, but also what it can reliably do with them. The results show a clear difference between \emph{representation} and \emph{generation}. The shared space supports cross-artifact retrieval and broadly preserves behavioral ordering. Training on behavior families helps the encoders ignore surface differences, such as two event log samples from the same process or two differently structured Petri nets that realize the same behavior. The explicit contrast between concurrency and interleaving also prevents equal visible traces from being treated automatically as complete behavioral equivalence.

This shared representation is most useful as a common search interface. For example, an event log can retrieve related process trees or Petri nets without a separate matcher for every pair of artifact types. The retrieved items can provide precedents for model reuse, variant comparison, or later conformance checking. Deterministic features nevertheless remain strong, especially for simple processes whose small observed language already describes much of their behavior. The learned representation becomes more competitive for larger structures, but its main advantage is one interface across artifact types, not the replacement of every specialized similarity measure. Moreover, the retrieval evidence comes from a controlled candidate set and does not yet establish performance in a large, deduplicated repository.

Process tree generation is less reliable. The grammar guarantees a well-formed tree, and the copy mechanism limits activity labels to the source vocabulary, but neither guarantee says that the generated tree preserves the source behavior. An incorrect operator or number of children near the start of the prefix can change the whole remaining structure. This often leads to omitted activities or overly compressed control flow. A finite event log can admit several correct models, so a generated tree need not match the chosen reference exactly; however, the lower behavioral and conformance scores show that ambiguity alone does not explain the errors. Allowing duplicate labels did not change the outputs for the two external event logs, so forced label uniqueness was not the cause of their poor results.

These findings suggest a workflow that \emph{retrieves, proposes, and validates}. The model first retrieves related artifacts, then proposes one or more process trees, and finally uses conformance checking and human review to decide whether a proposal is acceptable. Generation could be improved by producing several candidates and reranking them with behavioral evidence, training with objectives defined on complete decoded behavior, and allowing the model to report low confidence or abstain. The lack of improvement from simple mean fusion also suggests learning how much to trust each artifact type or combining their detailed source representations directly. The external event logs reveal sensitivity to inputs outside the synthetic training distribution; because they have no aligned reference artifacts in all three forms, they illustrate generation under distribution shift rather than deployment performance. The model should therefore be viewed as a retrieval and proposal tool, not as an unattended replacement for process discovery or conformance checking.

\FloatBarrier
\section{Limitations}\label{sec:threats}

Most evidence comes from synthetic behavior families produced by the same generator used to create the training data. Holding out complete families prevents artifacts from one family from appearing in different splits, but independently generated families were not globally deduplicated by normalized process tree or visible language. The synthetic data also omit timestamps, resources, lifecycle information, drift, and meaningful activity names. In addition, the generator supplies relation labels that would be harder to obtain for real artifacts. The results therefore show generalization to new families from the same generator, not transfer to industrial data or to behavior that is guaranteed to be globally distinct from the training set.

The two external event logs only illustrate how generation behaves under an input shift. They have no aligned reference process trees and Petri nets, so they cannot evaluate cross-artifact retrieval. The decoder is also limited to block-structured process trees. Some Petri net behavior cannot be expressed exactly in this grammar, which means that generation error may combine model error with a limitation of the output language.

The detailed evaluation uses a fixed subset of 48 families and one checkpoint from one training seed. The bootstrap intervals capture variation among those selected families, but not variation caused by corpus generation, initialization, training, or checkpoint selection. Some behavioral averages include only cases for which evaluation succeeded, and $d_B$ partly overlaps with descriptors used during training. Finally, the baselines do not cover every discovery method or a directly comparable learned cross-artifact system, and the study does not retrain separate ablations of the architecture, family design, curricula, fusion method, or loss terms. Stronger evidence will require real aligned artifacts, globally behavior-disjoint data, repeated runs, unconditional failure reporting, broader baselines, and retrained ablations.

\FloatBarrier
\section{Conclusion}\label{sec:conclusion}

\model demonstrates that heterogeneous process artifacts can currently be aligned more successfully than they can be translated. By training on relation-annotated behavior families, the neural system learns a common space in which event logs, process trees, and Petri nets from related families can be retrieved and compared. Grammar-constrained decoding solves a different problem: it ensures that every generated output is a well-formed process tree, but it does not ensure that the process tree preserves the source behavior.

The synthetic experiments and two real event log illustrations show that direct event log to process tree generation remains below the Inductive Miner baseline in the reported conformance checking experiments and that syntactic constraints alone do not prevent activity omission or incorrect control-flow placement. The present value of \model is therefore as a shared representation and retrieval layer that can propose candidates for subsequent validation, not as an autonomous process discovery system. The next step is to improve behavior-aware candidate generation and evaluate it on behavior-disjoint, real multi-artifact benchmarks, including structures outside the process tree grammar.
