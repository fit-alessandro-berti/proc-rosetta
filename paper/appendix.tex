\section{How the Training Data Was Generated}
\label{app:data-generation}

This supplementary document explains the data-generation pipeline used for the
main paper. The goal of the generator is simple: create many small process
behaviors, write each behavior in several forms, and keep an explicit record of
which forms share the same complete visible-trace language. The model can then
learn from paired examples instead of guessing which event log, process tree, and Petri net
belong together. This is the generator's chosen equivalence semantics; it does
not imply equality under every structural or partial-order semantics.

Figure~\ref{fig:app-generator-overview} summarizes the six stages detailed
below.

\subsection{What One Training Row Contains}
\label{app:data-row}

Each row in the generated data is a \emph{process sample}. A row contains four
main fields:
\begin{enumerate}
  \item a canonical process tree $T$;
  \item a generated event-log view $L$, stored as a finite list of visible activity
        traces;
  \item a Petri-net graph $G$, stored as typed nodes, labeled transitions,
        directed arcs, and initial/final marking vectors;
  \item an equivalence identifier $e$, shared by all rows in the same
        visible-trace equivalence family.
\end{enumerate}
The process tree is the decoder target. The generated event log is the finite
trace-based view of that family. The Petri-net graph is its graph-based view.
During training, rows with the same equivalence identifier are treated as
positive matches for the contrastive objective.

The persisted JSONL rows also store bookkeeping fields:
\texttt{model\_variant\_id}, \texttt{log\_view\_id},
\texttt{representation\_kind}, \texttt{equivalence\_level}, and
\texttt{metadata}. These fields make it possible to inspect which Petri-net
variant was used, which generator motif produced the family, and which
equivalence checks were passed.

All profiles share the following generator settings:
\begin{itemize}
  \item maximum activity labels: 30;
  \item maximum operator arity: 3;
  \item traces per generated event-log view: 128;
  \item activity-label reuse probability: 0.15;
  \item early leaf probability during process-tree recursion: 0.55;
  \item Petri representations per behavior family: 2;
  \item event-log views per behavior family: 2;
  \item controlled-motif context: randomized binary structure bounded to 4--12 nodes;
  \item family-type weights: 0.75 for ordinary process trees and $1/12$ for
        each of the three controlled motifs;
  \item strict minimum motif coverage: 8 families per motif in training and
        4 per motif in validation and test;
  \item enabled process-tree operators: \texttt{SEQ}, \texttt{XOR},
        \texttt{AND}, and two-child \texttt{LOOP}.
\end{itemize}
The \texttt{LOOP} operator is eligible in the ordinary-process-tree family but
is not required in every tree. The
generated and decoded loop form is the two-child form
$\operatorname{LOOP}(T_{\mathit{body}},T_{\mathit{redo}})$; the tokenizer mask
therefore emits \texttt{ARITY\_2} after a \texttt{LOOP} token. Because a loop
can repeat an arbitrary number of times, ordinary loop families use finite
process-tree playout to construct the observed trace pool rather than trying to
enumerate an unbounded language exhaustively.

\subsection{Why the Generator Uses Behavior Families}
\label{app:behavior-families}

The generator does not create isolated triples one by one. Instead, it creates
\emph{behavior families}. A behavior family combines one canonical process tree with
two Petri-net representations certified to have the same complete visible-trace
language (or related directly by isomorphic renaming for ordinary loop
families). Both rows in a family share:
\begin{itemize}
  \item the same canonical process tree;
  \item the same generated trace list;
  \item the same equivalence identifier.
\end{itemize}
They differ in their Petri-net graph. Sometimes the second graph is only a
renamed copy of the first graph. In other cases, the second graph uses a
different internal structure while keeping the same complete visible traces.
For example, the concurrency/interleaving family has the same linearized traces
but deliberately differs in partial-order semantics, recorded as
\texttt{partial\_order\_equivalent=false}. Thus the family identifier denotes
the explicit visible-trace equivalence used for training, not equivalence under
all behavioral notions.

The current configuration favors ordinary process trees while retaining all
three controlled family types. With the split sizes above, the deterministic
weighted quota allocator produces:

\toprule
Family type & Training families & Validation families & Test families \\
\midrule

Duplicate label vs. silent routing & 347 & 45 & 45 \\
Concurrency vs. explicit interleaving & 347 & 46 & 46 \\
Non-free-choice M pattern & 346 & 45 & 45 \\
\bottomrule

\end{center}

\subsection{Step 1: Choose the Family Type}
\label{app:choose-family-type}

For each split, the generator first computes how many behavior families are
needed. Because the current configuration stores four rows per behavior family,
16{,}384 training rows become 4{,}096 training families. The same calculation
turns 2{,}048 validation rows and 2{,}048 test rows into 512 families each.

The ordinary-process-tree family has weight 0.75; the duplicate-label/silent-
routing, concurrency/interleaving, and non-free-choice families have weight
$1/12$ each. The generator first reserves the strict per-type minimum and then
allocates the remaining families proportionally by the largest-remainder
method. It shuffles the resulting deterministic quota plan using a seed
derived from the global seed, the split name, and the phrase
\texttt{motif-quota-plan}. This gives a mixed order on disk while preserving
the planned weighted counts and minimum coverage.

The current run uses strict class coverage. Before replacing the data
directory, the generator verifies that every requested row count is divisible
by the number of rows per family and that the requested family count can meet
the per-motif minimum. An infeasible request therefore fails before the
existing split files are removed. A separate \texttt{best\_effort} mode is
available for small diagnostic datasets; it records motif and representation-
slot deficits instead of requiring them to be zero.

A complete behavior family is assigned to exactly one split, and its
equivalence identifier includes that split. The generator does not, however,
deduplicate complete visible languages across different families or splits.
Consequently, family members cannot leak across a split boundary, but equal or
near-equal behaviors can still occur independently in training and evaluation.

\subsection{Step 2: Build the Canonical Process Tree}
\label{app:build-tree}

The canonical process tree is the target representation used by the decoder.
There are two cases.

\paragraph{Ordinary-process-tree families.}
For ordinary-process-tree families, the generator first samples an unlabeled topology:
\begin{enumerate}
  \item The root is forced to be an operator selected by the family's quota plan.
  \item If the maximum depth has been reached, it creates an activity leaf.
  \item Otherwise, with probability 0.55 it also stops early and creates an
        activity leaf.
  \item If it does not stop, it chooses one operator from \texttt{SEQ},
        \texttt{XOR}, \texttt{AND}, and \texttt{LOOP}.
  \item For \texttt{SEQ}, \texttt{XOR}, and \texttt{AND}, it samples an arity
        between 2 and 3 and recursively generates the children.
  \item For \texttt{LOOP}, it recursively generates exactly two children: the
        body and the redo branch.
\end{enumerate}
The topology is rejected if it cannot hold the profile's activity floor.
Activity labels are then introduced as \texttt{a0}, \texttt{a1}, and so on:
the first required leaves are distinct, and subsequent leaves reuse an earlier
label with probability 0.15. Labels are normalized to \texttt{A0},
\texttt{A1}, and so on in depth-first tree order. Children of \texttt{XOR} and
\texttt{AND} nodes are sorted by a canonical structural key, so equivalent
child permutations do not become different targets. The final stored labels
are assigned later from the event-log view (Section~\ref{app:flatten-rows}).

After label assignment the tree is folded and accepted only when the final
decoder target satisfies its curriculum's size, depth, and activity bounds.
No loop is required and no post-generation sequence padding is used. An
exhausted attempt budget is an error rather than permission to emit an
out-of-profile target.

from the candidate-selection rule.

\paragraph{Controlled behavior families.}
The other three family types use small hand-defined canonical process trees:
\begin{itemize}
  \item duplicate-label vs. silent-routing families use
        $\operatorname{XOR}(\operatorname{SEQ}(A0,A1),
        \operatorname{SEQ}(A0,A2))$;
  \item concurrency vs. explicit-interleaving families use
        $\operatorname{AND}(A0,A1)$;
  \item non-free-choice M-pattern families use
        $\operatorname{XOR}(A0,\operatorname{AND}(A1,A2))$.
\end{itemize}
These process trees are intentionally small because their purpose is to isolate one
specific representation issue at a time. To avoid making every controlled case
too bare, the generator inserts each motif into a randomized binary structural
context bounded to 4--12 nodes. Context operators are selected from
\texttt{SEQ}, \texttt{XOR}, and \texttt{AND}; these semantically designed anchor
cases are excluded from the ordinary-tree operator-probability audit. The same
context is compiled around both Petri-net variants in the family.

\subsection{Step 3: Build Two Petri-Net Variants}
\label{app:build-petri-variants}

Each behavior family produces exactly two accepting Petri nets,
$N_v=(G_v,M^0_v,M^f_v)$ for $v\in\{0,1\}$. The graph $G_v$ contains places,
transitions, and directed arcs; $M^0_v$ and $M^f_v$ are its initial and final
markings. The two variants need not have the same nodes or topology. Instead,
the controlled families are constructed to satisfy
\begin{equation}
  \mathcal{L}_{\mathrm{vis}}(N_0)=\mathcal{L}_{\mathrm{vis}}(N_1),
  \label{eq:app-visible-language-invariant}
\end{equation}
where $\mathcal{L}_{\mathrm{vis}}$ contains complete firing sequences after
silent $\tau$ transitions have been removed. Step~4 verifies this invariant.
For ordinary loop families, whose languages are unbounded, a graph-isomorphism
certificate replaces enumeration. Step~6 later turns $N_0$ and $N_1$ into two
rows while keeping the same process tree, event-log view, and family identifier.

Figures~\ref{fig:app-ordinary-renaming}--\ref{fig:app-m-pattern} use standard
Petri-net notation: circles are places, a dot marks the initial token, a double
circle marks the final place, labeled rectangles are visible transitions, and
gray $\tau$ rectangles are silent transitions. The figures show the core motif;
the shared randomized structural context is omitted.

\paragraph{Duplicate-label vs. silent-routing families: move the choice.}
Both variants implement
$\operatorname{XOR}(\operatorname{SEQ}(A0,A1),
\operatorname{SEQ}(A0,A2))$. In $N_0$, the initial place has two outgoing
visible transitions, both labeled $A0$. Firing one of them simultaneously
selects the $A1$ or $A2$ branch. In $N_1$, a single $A0$ transition fires
first; only afterward do two competing silent transitions route the token to
$A1$ or $A2$. Thus the location and visibility of the choice differ, and the
number of $A0$ transitions differs, but both variants have exactly the visible
language $\{\langle A0,A1\rangle,\langle A0,A2\rangle\}$.

\paragraph{Concurrency vs. explicit-interleaving families: change the causal
structure.}
Both variants realize the complete visible traces
$\langle A0,A1\rangle$ and $\langle A1,A0\rangle$. The PM4Py-derived variant
$N_0$ uses a silent split to create two tokens. Consequently, $A0$ and $A1$
are enabled together and may overlap; a silent join waits for both. The
hand-built variant $N_1$ never holds two concurrent tokens. Instead, its upper
serial path spells out $A0$ then $A1$, and its lower path spells out $A1$ then
$A0$. The event sequences agree, but the partial-order semantics do not, so
the generator explicitly records
\texttt{partial\_order\_equivalent=false} for $N_1$.

\paragraph{Non-free-choice M-pattern families: change the conflict structure.}
The canonical process tree is
$\operatorname{XOR}(A0,\operatorname{AND}(A1,A2))$. In the block-structured
variant $N_0$, the first choice is global: either $A0$ fires, or a silent split
selects the parallel $A1$/$A2$ branch. In the hand-built M-pattern $N_1$, a
silent split first produces tokens in places $p_1$ and $p_2$. Transition $A0$
requires both tokens, while $A1$ competes for the token in $p_1$ and $A2$
competes for the token in $p_2$. Hence $A0$ shares an input place with each of
$A1$ and $A2$ but does not have the same preset, violating the free-choice
condition. Nevertheless, both variants complete exactly
$\langle A0\rangle$, $\langle A1,A2\rangle$, and
$\langle A2,A1\rangle$.

\subsection{Step 4: Check Behavioral Equivalence}
\label{app:equivalence-check}

For every family not handled by the ordinary-loop isomorphism shortcut, the
generator compares the visible trace sets returned for all Petri-net variants.
The checker explores firing sequences and records search states comprising the
marking, visible prefix, and firing count. It records traces that reach the
final marking, omits invisible transitions, and reports whether exploration
finished or a resource bound truncated it.

The current check uses these bounds:
\begin{itemize}
  \item a threshold of 5{,}000 visited search states;
  \item a threshold of 10{,}000 distinct complete visible traces;
  \item at most 32 visible activities per trace;
  \item at most $4\cdot32+|T|$ transition firings along a search path, where
        $|T|$ is the number of Petri-net transitions.
\end{itemize}
The implementation flags the search as incomplete when either count threshold
is exceeded or either path bound prevents further exploration. The trace set
returned up to that point must be nonempty and identical for every variant. If
all searches finish, the certificate status is \texttt{exact}; if a bound
truncates at least one search, the compared finite result receives status
\texttt{bounded}. The current configuration sets
\texttt{exact\_equivalence\_only\_for\_training} to false, so a bounded family
is eligible for any split. In the persisted data used here, however, every
controlled family received an \texttt{exact} certificate; there are no bounded
rows.

Ordinary loop families are handled separately because their language is
unbounded. Their second Petri net is an isomorphic clone of the PM4Py process-tree
conversion, so equivalence is certified structurally by the renaming
transformation. All ordinary-process-tree rows in the persisted data therefore store
the status \texttt{isomorphic}. Each accepted row includes the certificate
status, semantics, checked variant names, and reference-language size in its
metadata.

The generator also checks simple structural health conditions. In particular,
the final marking must be reachable and there must be no dead transitions. A
family that fails these checks is rejected.

\subsection{Step 5: Create the Generated Event-Log View}
\label{app:create-log-view}

After equivalence is checked or certified, the generator creates a trace pool.
For controlled families in the current data, the pool is the sorted exact
visible language returned by the completed checker. For ordinary loop
families, PM4Py performs $\max(256,4n)$ process-tree playouts for requested event-log
size $n$; the generator then deduplicates and sorts the observations. Thus the
current $n=128$ run draws 512 playout traces before deduplication. It creates
two event-log views per family and stores 128 traces in each view.

The current configuration uses \texttt{uniform\_variants} followed by
\texttt{resampled}, one for each of the two views. In \texttt{uniform\_variants}, the generator cycles through the
trace pool until it has 128 traces, then shuffles them with a deterministic
seed. If a behavior has only two variants, both recur; if the pool has more
than 128 variants, only its first 128 sorted entries are used before shuffling.

The generator also supports sparse, long-tail, incomplete, resampled, and noisy
modes for other experiments. The default split uses two clean views per family;
all stored trace-edit lists are
empty.

Family construction, quota order, and event-log-view shuffling use stable seeds;
loop trace pools are an exception: although a derived playout seed is recorded,
the current call does not apply it to PM4Py's playout randomness. Exact loop
trace pools are therefore not guaranteed by the generator seed alone and can
depend on ambient random state as well as the installed PM4Py version. The
persisted JSONL rows, rather than regeneration from seed alone, define the exact
loop event-log contents used in the study.

\subsection{Step 6: Flatten Families into Training Rows}
\label{app:flatten-rows}

The final step turns each behavior family into rows. With the current
configuration, each family has two generated event-log views and two Petri-net
variants, so it becomes exactly four rows (the Cartesian product of views and
variants). For either log view, the two representation rows are:
\[
\begin{aligned}
  &(\text{process tree}, \text{same event-log view},
    \text{Petri-net variant 0}, e),\\
  &(\text{process tree}, \text{same event-log view},
    \text{Petri-net variant 1}, e).
\end{aligned}
\]
Before these rows are stored, the generator scans the event-log view in its
persisted trace order and assigns \texttt{A0}, \texttt{A1}, and so on when each
activity first appears. Family-alphabet labels not observed in that finite view
are appended in stable tree/trace-pool order. The resulting map is applied to
the process tree, every trace event, and every visible Petri-net transition;
trace-edit provenance is relabeled by the same map. Consequently, all
modalities in a row use exactly the label scheme that an external event log
receives at inference time. The row records
\texttt{label\_scheme=first\_seen\_per\_log\_view} in its metadata.

\subsection{How the Row Is Used During Training}
\label{app:training-use}

At training time, each row is converted into tensors:
\begin{itemize}
  \item the process tree becomes a prefix token sequence with explicit arity
        tokens, preserving its stored first-seen activity labels;
  \item the generated traces become padded activity-token sequences;
  \item the Petri net becomes node-type indices, transition-label ids, marking
        features, and two adjacency matrices.
\end{itemize}
The batch collator also creates a positive-pair mask from strong behavior
identifiers. Exactly enumerated families use their exact behavior identifier;
isomorphic loop families use their equivalence identifier. If two rows have the same strong identifier, they are treated
as matching views of the same visible-trace equivalence family. Training batches
can also apply a consistent random renaming of activity labels within a family.
This preserves the behavior while reducing dependence on the literal label
names.

In short, the data-generation pipeline makes the supervision explicit. The
model sees a process tree, a finite generated event log, and a Petri-net graph; it also sees
which rows belong to the same visible-trace equivalence family. The generated
families therefore train the model to align artifact types by behavior rather
than by node names, transition counts, or one particular Petri-net structure.
